# Модель ошибок

## Правило

Внутри ядра — в хранилище, лексере, парсере, сервисе — ошибки только
бросаются. Решение о том, что ответить, принимается в одном месте: в функции
`handle`. Там исключение любого вида превращается в ответ клиенту, и дальше
не уходит ничего.

`handle` вызывают и цикл консольного клиента, и тесты, поэтому граница
проверяема: тесты `Handler.*` подают строки, приводящие к каждому виду ошибки,
и сверяют ответ.

Правило действует до конца курса. На этапе 15 `handle` будет вызывать сетевая
сессия, на этапе 16 — обработчик HTTP-запроса, и ошибка одного клиента не должна
ронять сервер.

## Иерархия

| Класс | Когда | Поля | Код на этапе 16 |
|---|---|---|---|
| `TaskQError` | корень, от `std::runtime_error` | — | 500 |
| `ParseError` | строка или тело (`num:`, `bin:`) не разобраны | причина, исходный ввод | 400 |
| `UnknownQueueError` | очереди нет | очередь | 404 |
| `UnknownTaskError` | задачи с таким номером не было | номер | 404 |
| `InvalidTransitionError` | переход запрещён автоматом | номер, из какого состояния, в какое | 409 |
| `WrongStateError` | `BUMP` выданной, `TYPE` завершённой | номер, состояние, операция | 409 |
| `TypeMismatchError` | `BUMP` нечисловой задачи | номер, ожидаемый и фактический вид | 409 |
| `OverflowError` | `BUMP` переполнил бы `int64` | номер | 409 |

Контекст лежит в полях, а не только в тексте `what()`. По полям на этапе 16
выбирается код ответа, и разбирать для этого строку сообщения недопустимо.

`UnknownTaskError` и `InvalidTransitionError` разведены намеренно: «задачи нет»
и «задача есть, но подтвердить её нельзя» — разные ответы, 404 и 409, и
клиент обязан их различать. Воркер, подтверждающий задачу, которую уже
подтвердил другой, получает 409.

`WrongStateError` — не переход: `TYPE` и `BUMP` состояние не меняют. Поэтому
у неё своё имя, а не перегруженный смысл `InvalidTransitionError`.

`OverflowError` в постановке не было — его нашёл фаззер (см. ниже).

Пустая очередь — не ошибка. Этап 2 сливал «очереди нет» и «очередь пуста»
в пустой `optional`. Теперь отсутствующая очередь — `UnknownQueueError`, а
пустой `optional` у `take` и `peek` означает ровно одно: работы нет. `POLL`
отвечает `(empty)`. Это обычный ответ воркеру, а не исключительная ситуация.

## Конечный автомат

```
             POLL              ACK
  Pending ─────────▶ Leased ─────────▶ Done
     ▲                 │  │
     └─────────────────┘  └──────────▶ Failed
         RELEASE                FAIL
```

Допустимые переходы собраны в одной функции `allowed(from, to)` в
`include/taskq/state.hpp`, а не размазаны по командам. Состояние каждой
задачи хранится в одном месте — `Service::states_` — и меняется только через
`transition_to`, которому предшествует `require_transition`. На этапе 11
переход должен стать атомарным; сделать атомарным можно только то, что
собрано в одной точке.

`Leased → Pending` — возврат аренды: воркер взял задачу и не подтвердил её.
Сейчас его вызывает команда `RELEASE`, на этапе 11 — сборщик просроченных
аренд. Это единственный обратный переход.

Таблица проверяется дважды: `static_assert` в самом заголовке и тест
`State.ExactlyFourTransitionsAreAllowed`, перебирающий все шестнадцать пар
по независимо записанному списку.

## Сильная гарантия пакетной постановки

`SUBMITBATCH build "make all" deploy prio=7 "ship it"` ставит несколько задач:
все или ни одной. `SUBMIT` — пакет из одной задачи, путь у них общий.

`BasicTaskStore::submit_batch` — copy-and-swap, но точечный: копируются не все
очереди, а только задетые пакетом.

```cpp
std::map<std::string_view, Queue> next;
for (const auto& [queue, task] : items) {
    // нет очереди — UnknownQueueError, ничего не изменено
    const auto [slot, first_time] = next.try_emplace(it->first);
    if (first_time) {
        slot->second = it->second;   // копия очереди
    }
    slot->second.push_back(task);    // копия задачи
}
for (auto& [queue, tasks] : next) {
    queues_.find(queue)->second.swap(tasks);   // noexcept — точка невозврата
}
```

Почему `swap` обязан быть `noexcept`: если последняя операция может бросить,
она перестаёт быть точкой невозврата. Часть очередей обменялась бы, часть
нет, и пакет оказался бы поставлен наполовину. Сильная гарантия выродилась
бы в базовую, причём молча: тест с броском при копировании этого не показал
бы, потому что бросает другая операция. `swap` у `std::vector` — `noexcept`,
это проверяет тест `Guarantee.CommitIsNoexcept`.

Доказательство гарантии — тест `Guarantee.BatchIsAllOrNothing`. Тип
`ThrowOnNthCopy` бросает на N-й операции копирования. Пакет из четырёх задач в
три очереди делает семь копирований — три копии очередей и четыре копии
задач, — и тест перебирает бросок на каждом, в том числе в середине пакета.
После каждого броска очереди совпадают с исходными.

На уровне сервиса к хранилищу добавляется учёт состояний. Записи о новых
задачах готовятся в отдельной таблице до постановки и переносятся в `states_`
через `merge` после неё. `merge` переносит узлы, не выделяя памяти, и бросить
может только сравнение ключей — а сравнение целых не бросает. Номера задач
занимаются последними: неудачный пакет номеров не тратит (тест
`Executor.BatchWithUnknownQueueSubmitsNothing`).

### Почему не копия всех очередей

Методичка показывает полную копию `queues_` — верный и самый простой вариант.
Его цена — копия всего хранилища на каждый пакет, в том числе очередей,
которых пакет не касается. Точечная копия платит только за задетые очереди.
Полностью избавиться от копирования можно журналом отката, но он в разы
сложнее и сам должен быть написан так, чтобы откат не бросал. Вопрос
вернётся на этапе 11 вместе с шардами.

### POLL и RELEASE

Одиночные переходы тоже не теряют задачу. Наивный `POLL` — «забрать из
очереди, потом записать в аренду» — при нехватке памяти на узел `map` терял
бы задачу: из очереди она ушла, в аренду не попала. Поэтому место в
`leases_` готовится заранее, а задача переезжает в него перемещением, которое
не бросает. `RELEASE` делает наоборот: сначала копия задачи в очередь (бросок
оставляет аренду целой), затем удаление аренды, которое не бросает.

## Два пути: исключения и ошибка-значение

Разбор строки написан двумя способами:

- `parse(line)` бросает `ParseError`;
- `try_parse(line)` возвращает `Result<Command, ParseError>`.

`Result` — минимальная собственная версия `std::expected` поверх
`std::variant`: проект на этом этапе собирается под C++17, а `std::expected`
появился только в C++23. Интерфейс повторяет стандартный, и на этапе 5
замена сводится к замене имени. `std::optional` для этого не подходит: пустой
`optional` говорит «не получилось», но не говорит почему.

Разбор `SUBMIT` и проверки ввода общие для обоих путей и возвращают причину
значением; путь на исключениях получает результат через `value()`, который у
нашего `Result` бросает саму ошибку. Так же устроен лексер: основная функция —
`try_tokenize`, а `tokenize` — это `try_tokenize(...).value()`.

Сравнение по трём пунктам.

**Читаемость.** В `parse` каждая проверка — одна строка `fail(...)`, ошибка
лексера пролетает сама. В `try_parse` после каждого вызова лексера стоит
проверка и ручной возврат, а доступ к токенам идёт через `*all`. Зато
сигнатура `try_parse` честно говорит, что разбор может не удаться и чем;
сигнатура `parse` об этом молчит.

**Стоимость.** Когда ошибок нет — одинаково: утилита `taskq_error_cost`
в оптимизированной сборке даёт около 165 нс на строку в обоих путях.
Исключение, которое не бросили, по времени бесплатно. Когда ошибка в каждой
строке, бросок дороже примерно на порядок: около 3200 против 320 нс.

**Проброс через десять уровней.** Тест `TryParse.ErrorThroughTenLevels`:
исключение пролетает десять уровней само, промежуточные функции о нём не
знают. Ошибку-значение каждый из десяти уровней обязан проверить и передать
дальше; пропуск любой проверки молча теряет ошибку.

Где в этом проекте уместнее что. Ошибка ожидаема и часта — разбор ввода,
`POLL` пустой очереди — значит, значение: `Result` у разбора, `optional` у
`take`. Ошибка исключительна и должна пролететь от хранилища до границы —
неизвестная очередь, запрещённый переход, `bad_alloc` посреди пакета —
значит, исключение.

## Звёздочка: цепочка контекста

Ошибка из глубины не знает, какая команда её вызвала: `UnknownQueueError`
несёт имя очереди, но не то, что это был `SUBMITBATCH`. Сервис прикладывает
это знание через `std::throw_with_nested`:

```cpp
try {
    return run(command);
} catch (...) {
    std::throw_with_nested(TaskQError("while executing " + describe(command)));
}
```

Граница разворачивает цепочку функциями `root_cause` и `context_of`
(`src/errors.cpp`, на основе `std::nested_exception::nested_ptr`): ответ
строится по исходной причине, контекст дописывается в скобках:

```
> ACK 9
ERR no such task: 9 (while executing ACK 9)
```

Это трассировка доменных операций, а не стека вызовов: в ней только то, что
осмысленно для читающего лог. Тест `Errors.NestedChainUnwindsToRootCause`
разворачивает цепочку из трёх звеньев.

Это единственный `catch` внутри ядра. Правило он не нарушает: запрещено
ловить и проглатывать, а здесь ловится, чтобы бросить снова, с добавленным
контекстом.

## Домашнее задание: фаззер

`tests/test_fuzz.cpp` прогоняет через `handle` по тысяче входов каждого вида и
проверяет инварианты сервиса: корректные имена очередей, тела задач —
валидный UTF-8 не длиннее предела, каждая задача в очереди имеет состояние
`pending` именно в этой очереди, и каждая задача в состоянии `pending` лежит
в очереди. Зерно фиксировано, упавший прогон воспроизводится.

Находки на версии с проверками этапа 2 (каждая закрыта тестом):

| Вход | Что было | Исправление | Тест |
|---|---|---|---|
| `CREATE "   "`, `" build"`, табуляция, имя в 200 символов | очередь с таким именем | `queue_name_problem` | `Validate.QueueNames` |
| тело в мегабайт | целиком в очереди | предел строки 64 КиБ | `Validate.ParserRejectsWhatTheFuzzerFound` |
| `SUBMIT build make\xd0` | обрезанный UTF-8 в теле, уходил воркеру | `is_valid_utf8` на всю строку | `Validate.Utf8` |
| `BUMP 2 -9223372036854775808` | переполнение знакового целого, UB; санитайзер остановил прогон | `checked_add`, `OverflowError` | `Executor.BumpOverflowIsAnErrorNotUndefinedBehaviour` |

Типовые находки по методичке — отрицательный приоритет, приоритет больше 9,
`ACK` несуществующей задачи — дефектами не оказались: разбор этапа 2
приоритеты уже проверял, а `ACK` неизвестного номера даёт `UnknownTaskError`.
Такие входы оставлены в прогоне, чтобы это поведение не потерялось.

## Этап 5: Result заменён на std::expected

С переходом на C++23 собственный `Result` удалён, его место занял
`std::expected`. Интерфейс тот же — `has_value`, `operator*`, `error`, неявное
построение из значения и из `std::unexpected`, — и вызывающий код поменялся
почти механически.

Отличие одно, и оно существенно: `value()` у `std::expected` бросает не саму
ошибку, а `std::bad_expected_access<E>`, внутри которой ошибка лежит. Лексер
больше не сводится к `try_tokenize(line).value()`, а разбор `SUBMIT` в пути на
исключениях — к `try_parse_submit(line).value()`: граница получила бы
`bad_expected_access` вместо `ParseError` и ответила бы «internal error».
Поэтому оба места проверяют результат и бросают `error()` явно. Тест
`Expected.ValueThrowsBadExpectedAccess` фиксирует это поведение.

Заодно появились `and_then`, `transform` и `or_else` — цепочки шагов, каждый
из которых может не удаться, без ручной проверки после каждого
(`Expected.MonadicChaining`). Это ответ стандарта на главный недостаток второго
пути из сравнения выше — ручной проброс ошибки через уровни.
