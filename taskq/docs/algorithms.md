# Алгоритмы вместо циклов (этап 8, пункт 5)

Правило, по которому шёл проход: цикл заменяется алгоритмом, если у цикла
есть имя — «найти», «посчитать», «удалить такие», «все ли», «есть ли
хоть один», «свернуть», «преобразовать каждый». Имя алгоритма говорит, что
делается; цикл заставляет читателя восстановить это по телу. Если имени у
цикла нет — конечный автомат, разбор с откатом, шаг, меняющий сам
контейнер, по которому идёт обход, — цикл остаётся, и ниже сказано почему.

## erase-remove и `std::erase_if`

Идиома erase-remove — для последовательных контейнеров:

```cpp
returned.erase(std::ranges::unique(returned).begin(), returned.end());
```

Это REAP: номера просроченных и брошенных аренд собраны в один вектор и
отсортированы, `unique` сдвигает первые из каждой серии равных в начало и
возвращает хвост, `erase` хвост удаляет. `unique`, как и `remove`, ничего не
удаляет сам — забыть `erase` значит оставить в векторе повторы в
перемещённом состоянии, и задача вернулась бы в очередь дважды
(`Deadlines.AbandonedAndExpiredCountedOnce`).

Для ассоциативных контейнеров erase-remove неприменим — их элементы
переставлять нельзя, — и с C++20 удаление по условию — `std::erase_if`,
перегруженная для всех стандартных контейнеров. В очереди она не
понадобилась по честной причине: везде, где удаляется по условию, задачу
надо ещё и забрать, а `erase_if` только удаляет (ниже — PURGE).

## Что осталось циклами и почему

- **`promote_due`** — «пока начало индекса по сроку не позже now: перенести
  задачу в очередь и удалить узел». Каждый шаг меняет само дерево, по
  которому идёт; алгоритма «обработать и удалить, пока условие» нет.
- **`purge`, отложенные** — цикл `it = erase(it)`: задачу надо переместить
  в результат до удаления узла, `std::erase_if` только удаляет.
- **`submit_batch`** — вставка с откатом: в `catch` откатываются ровно
  сделанные шаги, и порядок важен.
- **`submit_all`** — на каждый элемент две вставки и счётчик номеров;
  `views::enumerate` дал бы номер, но два побочных эффекта на шаг
  остались бы.
- **`tasks_where`** — материализация ленивого конвейера обычным циклом
  сознательно, с этапа 5: `ranges::to` для прямого диапазона проходит его
  дважды, и предикаты вызывались бы вдвое чаще (`List.PipelineIsLazy`).
  В новой `list_page` — `ranges::transform`: он проходит диапазон один
  раз, а цикл в `tasks_where` оставлен как есть, чтобы не менять тест
  ленивости этапа 5.
- **Лексер и разбор именованных аргументов в реестре** — автоматы с
  курсором по токенам.
- **Цепочка вложенных исключений** (`errors.cpp`) — следующий элемент
  получается из предыдущего, диапазона заранее нет.
- **`from_hex`** (`service.cpp`) — шаг 2 и ранний выход на плохой цифре;
  `views::chunk(2)` с `transform` пришлось бы прерывать исключением.
- **Проверка UTF-8** (`validate.cpp`) — длина шага зависит от первого байта.
- **Собственные таблицы** — обход цепочки и пробег по ячейкам: это и есть
  реализация поиска.
- **`task_key.cpp`, сдвиги по 8 бит** и **`main.cpp`** (аргументы, цикл
  `getline`).
