# Заметки

## Этап 2. Почему тело задачи — `std::variant`, а не `std::any`

`std::any` выглядит удобнее: в него можно положить что угодно, и для нового
вида тела задачи ничего не надо объявлять заранее. В этом проекте он хуже по
двум причинам.

**Стоимость доступа.** `std::variant<TextPayload, NumericPayload, BinaryPayload>`
хранит тело внутри себя: размер объекта — максимум из альтернатив плюс индекс,
отдельная память не нужна. Доступ — проверка индекса и смещение. `std::any`
для всего, что не помещается в его небольшой внутренний буфер (структура со
строкой в libstdc++ не помещается), выделяет память в куче — то есть каждая
задача в очереди стоила бы ещё одну аллокацию. Доступ идёт через
`std::any_cast`, который сравнивает `typeid`, — это дороже сравнения целого
индекса, а сервис задач перебирает очереди постоянно.

**Что проверяет компилятор.** Набор альтернатив `variant` известен на этапе
компиляции. `std::visit` с перегруженным набором лямбд не соберётся, если
какая-то альтернатива не обработана: появится, скажем, тело-ссылка на файл —
компилятор покажет каждое место, где её надо учесть (`type_name`, `to_string`,
`size`). С `std::any` о новом виде тела узнает только тот код, который о нём
знает; остальные `any_cast` молча промахнутся во время выполнения, и воркер
получит задачу, которую не сможет описать.

`std::any` уместен там, где набор типов действительно открыт: например,
произвольные метаданные, которые сервис лишь хранит и отдаёт обратно, не
заглядывая внутрь. У тела задачи набор видов закрыт и определяется
протоколом, поэтому `variant` точнее выражает намерение и дешевле стоит.
