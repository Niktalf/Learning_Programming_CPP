# Этап 10. Доменные события

## Что публикуется

Каждый переход автомата состояний (`state.hpp`) публикует ровно одно событие
(`docs/events.puml`):

| Событие | Переход | Команда | Поля |
|---|---|---|---|
| `TaskSubmitted` | → Pending | SUBMIT, SUBMITBATCH (по событию на задачу) | задача, очередь, приоритет |
| `TaskLeased` | Pending → Leased | POLL | задача, воркер (пусто — анонимная выдача) |
| `TaskCompleted` | Leased → Done | ACK | задача |
| `TaskFailed` | Leased → Failed | FAIL, попытки исчерпаны | задача, причина: `attempt 3 of 3` |
| `TaskReturned` | Leased → Pending | RELEASE, REAP, FAIL с повтором | задача, причина: `released`, `expired`, `abandoned`, `retry 2 of 3` |
| `TaskCancelled` | Pending → Cancelled | PURGE | задача |

Первые четыре — из постановки этапа. Два добавлены, потому что без них поток
событий говорит неправду. Без `TaskReturned` подписчик увидел бы вторую выдачу
задачи, не узнав, что первая кончилась, — и не отличил бы повтор после FAIL от
ошибки сервиса. Без `TaskCancelled` снятая PURGE задача осталась бы у подписчика
ожидающей навсегда. Добавить событие — альтернатива в `DomainEvent`; адаптер и
потребитель без обработчика для неё не скомпилируются (`std::visit` с
`overloaded`).

Чтения (STATUS, LIST, PEEK, INFO) и правки ожидающей задачи (BUMP, DELAY)
событий не дают: перехода нет. Отвергнутый переход — ACK невыданной задачи,
FAIL после ACK — событий не даёт тоже: `Lifecycle::require` бросает до любого
изменения.

## Где события рождаются и где публикуются

```
Service::execute ─► команда ─► Lifecycle::require    (может бросить — ничего не изменено)
                             ─► подготовка, фиксация
                             ─► Lifecycle::commit
                             ─► record (журнал переходов)
                             ─► raise (событие в outbox_)
                 ─► publish_events: outbox_ → IEventPublisher::publish
```

Событие порождает `Service`, а не `Lifecycle`: автомат знает только «из» и «в»,
а событию нужны очередь, приоритет, воркер, причина. `raise` стоит рядом с
`record` — там же, где пишется журнал переходов, и по той же причине: переход
уже зафиксирован. `raise` не бросает: если на событие не хватило памяти,
переход назад не откатить, и событие считается потерянным.

Публикует `Service::execute` после команды — и при неудачной тоже: у REAP
базовая гарантия, и задачи, возвращённые до отказа, уже в очередях. На этапе 11
события будут собираться под мьютексом шарда, а публиковаться после его
освобождения: отправка в брокер — ввод-вывод с непредсказуемой задержкой.

## Ключ сообщения

Ключ сообщения Kafka — номер задачи.

Kafka хранит порядок только внутри партиции, а партиция выбирается по хешу
ключа. Поэтому все события одной задачи ложатся в одну партицию и приходят
подписчику в том порядке, в каком произошли: постановка — раньше выдачи,
выдача — раньше подтверждения. Подписчик не увидит `TaskCompleted` раньше
`TaskSubmitted`. Это проверяет сквозной тест
`Kafka.LifecycleOfOneTaskKeepsItsOrder`: у каждой задачи одна партиция, цикл
задачи 1 — постановка, выдача, возврат, повторная выдача, подтверждение — прочитан
в исходном порядке, номера событий задачи идут подряд.

Между задачами порядка нет, и он не нужен: жизненные циклы разных задач
независимы.

### Компромисс: ключ — очередь

Ключ-очередь тоже сохранил бы порядок по задаче: задача не переходит между
очередями, и все её события оказались бы в партиции её очереди. Сверх этого он
дал бы порядок между задачами одной очереди — подписчик видел бы постановки в
том порядке, в каком они шли в очередь.

Цена — параллелизм. Все события одной очереди шли бы в одну партицию, а
партицию в группе читает ровно один потребитель. При одной большой очереди
`build` три партиции топика превратились бы в одну работающую, и второй и третий
потребитель группы простаивали бы. Ключ-задача размазывает события по всем
партициям, и потребители группы делят работу поровну.

Порядок между задачами очереди подписчику этого сервиса не нужен: решения
принимаются по каждой задаче отдельно. Поэтому выбран ключ-задача. Если бы
подписчик по событиям восстанавливал содержимое очереди целиком — например,
показывал бы её на экране в порядке постановки, — правильным был бы
ключ-очередь.

## Тело сообщения

Строка, поля через табуляцию (`event_wire.hpp`):

```
9c41…2e	1	submitted	7	build	0
9c41…2e	2	leased	7	w1
9c41…2e	3	completed	7
```

Первые два поля — издатель и номер события задачи. Издатель — случайный
идентификатор процесса-сервиса; номер — счётчик событий задачи у этого издателя.
Тройка «издатель, задача, номер» однозначно называет событие: по ней потребитель
узнаёт повтор, а по разрыву в номерах — пропуск. После последнего события задачи
(`is_final`) адаптер забывает её счётчик, и таблица счётчиков не растёт с числом
выполненных задач.

## Домашнее задание: брокер недоступен

| Выбор | Что происходит при лежащем брокере |
|---|---|
| Блокироваться, пока брокер не примет | Отказ брокера становится отказом сервиса: воркеры не могут ни взять, ни сдать задачу |
| Копить без предела | Отказ брокера становится исчерпанием памяти |
| Терять события | Сервис работает, подписчики получают поток с дырами |

**Выбрано: копить с пределом, при переполнении — терять и показывать дыру.**

1. `send` обёртки не блокируется и не ходит в сеть. Пока брокер лежит, события
   ждут в очереди клиента и уходят, когда он поднимется (тест
   `Kafka.CommandsWorkWhileBrokerIsDown`).
2. Очередь ограничена: `KafkaOptions::max_queued`, по умолчанию 100 000.
3. Очередь полна — `send` бросает. Адаптер исключение не ловит: решение
   принимает прикладной слой. `Service::publish_events` считает событие
   потерянным (`Service::lost_events`), переход выполнен, клиент получает `OK`
   (тест `Kafka.FullQueueLosesEventsButKeepsTasks`). При выходе `taskq_cli`
   печатает в stderr, сколько событий потеряно.
4. Номер события задачи адаптер расходует до `send` — даже если `send` бросит.
   Поэтому потеря видна подписчику: после 2 придёт 4, и `taskq_tail` напечатает
   `gap on task 7: expected event 3, got 4 — check STATUS 7`.
5. Брокер не вернулся за пять минут — сообщение выбрасывает библиотека,
   обработчик доставки в фоновом потоке считает потери в `atomic` и пишет в
   stderr первую и каждую тысячную.
6. При остановке сервис ждёт отправки не дольше двух секунд.

### Можно ли потерять событие о выполнении задачи

Зависит от того, кто его читает.

**Подписчик статистики** — сколько задач выполнено за час, средняя длина
очереди. Потеря терпима: цифра станет чуть меньше настоящей, и по разрыву в
номерах видно, на сколько. Ради него не стоит останавливать сервис.

**Подписчик, запускающий следующий шаг** — по `TaskCompleted` задачи «собрать»
ставится задача «развернуть». Для него потеря недопустима: следующий шаг не
запустится никогда, и работа встанет без единой ошибки в журнале. Разрыв в
номерах он увидит, но только когда придёт следующее событие той же задачи — а
после `TaskCompleted` их не бывает.

Поэтому выбор «терять» здесь верен лишь вместе с оговоркой: события этого
сервиса — уведомления, а не команды. Подписчик, которому нужна гарантия,
не должен полагаться на одно событие: он сверяется с источником правды —
`STATUS` задачи — по таймауту или при разрыве. Если такой подписчик
появится и сверка ему не подходит, выбор надо менять: не терять событие,
а отказывать в ACK, пока очередь клиента полна, — тогда воркер повторит ACK,
и задача останется выданной до тех пор, пока событие о её выполнении не
сможет уйти. Это ровно та связь доступности сервиса с брокером, которой
сейчас удалось избежать, и платить её стоит, только когда событие —
часть обработки, а не отчёт о ней.

## Звёздочка: идемпотентный потребитель

At-least-once — гарантия брокера, а не свойство приложения. `taskq_tail`
фиксирует смещение вручную (`auto_commit = false`) и только после того, как
пачка обработана: упавший до фиксации потребитель получит пачку снова. Для
сервиса задач цена повтора нагляднее всего: без защиты счётчик выполненных задач
задваивается, и по нему нельзя судить о проделанной работе. Это та же беда, что у
самих задач: воркер, упавший между выполнением и ACK, выполнит задачу второй
раз после возврата аренды.

Защита — на стороне потребителя:

- **идентификатор события** — издатель, задача, номер;
- **окно уже обработанных** (`SeenEvents`): последние N идентификаторов,
  старейший вытесняется первым (`--remember=N`, по умолчанию 100 000);
- **окно переживает перезапуск** (`--state=FILE`): идентификаторы пачки
  дописываются в файл до `commit` и читаются при запуске;
- **итоги** (`Tally`) — сколько поставлено, выполнено, провалено, — считаются
  только по новым событиям и печатаются при остановке.

Проверка: второй потребитель другой группы с тем же файлом состояния читает
топик с начала — это и есть повторная доставка:

```
$ taskq_tail --state=seen.txt
[2:0] task 1 submitted to build (priority 0)
[2:1] task 1 leased by w1
[2:2] task 1 completed
[1:0] task 2 submitted to build (priority 0)
[1:1] task 2 leased
[1:2] task 2 failed (attempt 1 of 1)
^C
submitted 2, completed 1, failed 1, cancelled 0; duplicates skipped 0
$ taskq_tail --group=again --state=seen.txt
[2:0] duplicate ec87…89:1:1 skipped
…
^C
submitted 0, completed 0, failed 0, cancelled 0; duplicates skipped 6
```

Чего это не даёт — exactly-once. Печать и запись файла не атомарны вместе:
упавший между ними потребитель обработает пачку второй раз. Закрыть щель можно,
только сделав обработку и фиксацию одной транзакцией — транзакции Kafka или
хранение смещений и итогов в одной базе. В выданной обёртке транзакций нет.
