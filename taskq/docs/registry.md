# Этап 6: реестр команд

До этапа 6 команда проходила пять мест: структура в `command.hpp`, ветка в
`parse`, вторая — в `try_parse`, ветка в `std::visit` исполнителя и строка в
`describe` для цепочки контекста. Реестр сводит это к одной строке:

```cpp
table.register_command("PEEK", &Service::peek);
```

и методу сервиса:

```cpp
Response peek(QueueName queue) const;
```

Число, порядок и типы аргументов, подсказка об использовании, место тела
задачи в строке и контекст для цепочки исключений выводятся из сигнатуры.

Файлы: `include/taskq/function_traits.hpp`, `include/taskq/convert.hpp`,
`include/taskq/registry.hpp`, `src/commands.cpp`; курсор лексера —
`TokenCursor` в `lexer.hpp`. Старые `command.hpp` и `parser.*` удалены,
`executor.*` переименованы в `service.*`: исполнителя как отдельной сущности
больше нет, команды — методы сервиса.

## Обработчик — метод

Обработчикам нужны закрытые поля `Service`: аренды, состояния, реестр
воркеров. Свободной функции пришлось бы открыть их или стать другом. Поэтому
обработчики — методы, а реестр принимает указатель на метод наравне с
функцией.

`function_traits` для указателя на метод даёт, кроме результата и
параметров, `object` — класс с константностью метода: `Service` у `ack`,
`const Service` у `status`. Реестр приписывает к параметрам ссылку на объект
первым параметром, и для него `&Service::ack` и функция
`ack(Service&, TaskId)` — одно и то же. Вызов — `std::invoke`, которому всё
равно, что вызывать.

Константность видна реестру: `Bound::reads_only()` истинно у STATUS, TYPE,
LIST и PEEK. Константный метод не может ничего изменить по ошибке — это
проверяет компилятор, а не ревью.

## Типы аргументов

| Тип | Что это | Проверка | В подсказке |
|---|---|---|---|
| `QueueName`, `WorkerName` | имена | `queue_name_problem`, `worker_name_problem` | `<queue>`, `<worker>` |
| `TaskId` | номер задачи | только цифры, без знака и ведущих нулей, не ноль | `<id>` |
| `Priority` | `prio=N` | 0..9 | `[prio=0..9]` |
| `MinPriority` | `prio>=N` | 0..9 | `[prio>=0..9]` |
| `Kind` | `type=…` | text, number или binary | `[type=text\|number\|binary]` |
| `Limit` | `limit=N` | неотрицательное число | `[limit=N]` |
| `std::chrono::seconds` | задержка DELAY | 90, 90s, 15m, 2h, не больше года | `<delay>` |
| `Tail` | тело SUBMIT — остаток строки | — | `<body...>` |
| `Batch` | пакет SUBMITBATCH — все оставшиеся токены | группы «очередь [prio=N] тело» | `<queue> [prio=0..9] <body> ...` |
| числа | шаг BUMP | `from_chars` до конца токена | `[number]` |

### Порядок веток: TaskId раньше чисел

`TaskId` — псевдоним `std::uint64_t`, а не отдельный тип. Для
`if constexpr` это значит: ветка `is_arithmetic_v<T>` подходит и номеру
задачи. Если поставить её первой, ветка `TaskId` никогда не выполнится, и
«+7» или «007» станут задачей номер 7 — `from_chars` разбирает их без
жалоб. Поэтому ветка `TaskId` стоит выше; тест
`Convert.TaskIdBranchComesBeforeNumbers`.

Обратная сторона псевдонима: любой параметр `uint64_t` разбирается как
номер задачи. На Linux `std::size_t` — тот же тип, и предел `LIST` пришлось
сделать отдельным типом `Limit`, иначе `limit=0` отвергался бы как «не номер
задачи». Настоящее решение — сильный тип `TaskId` вместо псевдонима; это
затронуло бы весь проект и оставлено на потом. Ровно это и показывает
историческая версия на `enable_if`: «TaskId раньше чисел» там выражается не
порядком, а вычитанием — условие для чисел содержит `!is_task_id<T>`.

## Раскладка строки: именованные аргументы и `Tail`

У `SUBMIT` необязательный приоритет стоит перед телом:

```
SUBMIT build prio=5 make all
SUBMIT build make all
```

Тело — весь остаток строки, с кавычками как есть. До реестра `parse`
разбирал строку дважды: сначала с хвостом после третьего токена, и если
третий не приоритет — с хвостом после второго. Это особый случай, а
постановка требует, чтобы реестр умел это выразить.

Выражается так: `optional<Priority>` — именованный аргумент. Его место в
строке определяет не позиция, а префикс `prio=`. Реестр раскладывает строку
по параметрам курсором лексера (`TokenCursor`), смотрит на следующий токен
и, если у него подходящий префикс, отдаёт его приоритету; если нет —
приоритета нет, и с этого места начинается тело. Курсор понадобился потому,
что `tokenize(line, n)` режет строку на заранее заданное число токенов: при
отсутствующем приоритете он попытался бы разобрать кавычки в первом слове
тела, которое разбирать нельзя.

Именованные аргументы подряд принимаются в любом порядке:
`LIST build limit=5 prio>=3` и `LIST build prio>=3 limit=5` — одна команда.
Повтор — лишний аргумент: «unexpected argument: limit=2».

Форма параметров проверяется при компиляции:

```
обязательные*  именованные*  (необязательные* | Tail | список токенов)
```

Обычный необязательный аргумент — по позиции, и `Tail` после него
невозможен: строку «POLL q 5 штук» нельзя было бы разрезать однозначно.
Именованный перед `Tail` — можно, префикс снимает неоднозначность.

Раскладка и преобразование разделены: `lay_out` знает только форму и
раскладывает токены по местам; `convert_all` превращает их в аргументы по
типам. Первое — работа во время выполнения над таблицами, вычисленными при
компиляции (`Shape::slots`, `Shape::prefixes`); второе — раскрытие пакета
параметров.

## Подсказка вместо «expects a task id»

Любая ошибка разбора аргумента — `ParseError` с причиной, к которой реестр
приклеивает подсказку тем же `std::throw_with_nested`, что и контекст
исполнения:

```
ERR task id must be a positive number: sleeping (usage: ACK <id>)
ERR missing <body...> (usage: SUBMIT <queue> [prio=0..9] <body...>)
ERR unexpected argument: limit=2 (usage: LIST <queue> [prio>=0..9] [type=text|number|binary] [limit=N])
```

Ревью этапа 5 отмечало, что «not a number: sleeping» само по себе не говорит,
где ошибка. Подсказка говорит, и забыть её обновить нельзя: она выводится из
той же сигнатуры, по которой разбираются аргументы.

## `if constexpr` против `enable_if`

`include/taskq/legacy_convert.hpp` — `convert` для строки, `Priority`,
`TaskId` и прочих чисел на четырёх перегрузках с `std::enable_if`. Сравнение
по объёму, читаемости, диагностике и цене пятого случая — в комментарии в
начале файла. Тест `Convert.LegacyAgreesWithModern` проверяет, что обе
версии ведут себя одинаково.

## Концепция `CommandHandler`

Пять требований с именами: `HasSignature`, `ReturnsResponse`,
`TakesContextFirst` (у метода — сам объект, `Service&` или
`const Service&`), `ArgumentsSupported`, `ArgumentOrderValid`. На
`tests/compile_fail/bad_handler.cpp` (приоритет как `bool`) GCC 15 называет
невыполненное требование:

```
required for the satisfaction of 'ArgumentsSupported<F>'
```

Тест `taskq_bad_handler_fail` проверяет и отказ сборки, и имя требования.

## Домашнее задание: DELAY, PURGE, PEEK

Каждая — строка регистрации и метод. Кроме метода понадобились операции
хранилища (`delay`, `purge`, константный `find`) и, для PURGE, новое
состояние.

**PEEK** показывает то, что выдал бы POLL, не выдавая. Константный метод.

**PURGE** снимает все ожидающие задачи очереди. Им нужно конечное
состояние, и это `Cancelled` — переход `Pending → Cancelled` добавлен в
автомат (`state.hpp`, тест `State.ExactlyFiveTransitionsAreAllowed`, и в
копию автомата в модуле этапа 5). Выданные воркерам задачи PURGE не трогает:
их судьбу решает воркер. Сильная гарантия: очередь отдаётся целиком обменом с
пустой, переходы фиксируются `transition_to`, и ни то ни другое не бросает.

**DELAY** — самая интересная из трёх. Задача остаётся в своей очереди, на
своём месте и с прежним приоритетом, но до указанного момента POLL её не
выдаёт.

### Как DELAY уживается с приоритетной выборкой

Выборка «следующей» — минимум ключа `TaskKey` (приоритет по убыванию, затем
порядок постановки) среди задач очереди. С DELAY — среди *готовых*: тех, чьё
время наступило. Отложенная задача не участвует в сравнении вовсе — её ключ
не важен, пока не наступило её время. Тест
`Commands.DelayedTaskIsSkippedUntilItsTime`: отложенная задача с
приоритетом 9 не загораживает задачу с приоритетом 0.

Сейчас это дёшево сделать неправильно и дорого — правильно, а стоит одинаково:
очередь — вектор, поиск линейный, и отложенная задача просто пропускается
фильтром (`next_in` в `task_store.hpp`).

На этапе 7 вектор сменит приоритетная очередь — куча, — и пропустить
вершину кучи нельзя: смотреть можно только на неё. Отложенная задача с
высоким приоритетом окажется на вершине и закупорит очередь: POLL видит её,
она не готова, а остальные под ней недоступны. Вывести её из кучи и
вернуть потом — значит хранить отложенные отдельно.

Вывод: отложенные задачи должны жить во втором индексе — упорядоченном по
времени готовности, — а в кучу попадать, когда их время наступило. POLL
сначала переносит из второго индекса всё, что созрело, и только потом берёт
вершину кучи. На этапе 8 этот индекс появится. Таблица `not_before_` в
хранилище — его зачаток: уже сейчас время готовности хранится не в задаче,
а отдельно, по номеру.

Часы сервиса внедряются (`Service::set_clock`): тест двигает время сам, не
засыпая. На этапе 11 те же часы понадобятся срокам аренды.

## Звёздочка: `StaticRegistry`

`include/taskq/static_registry.hpp`. Имя команды — параметр шаблона, и
обработчиком может быть метод:

```cpp
using Commands = StaticRegistry<Tally, Command<"BUMP", &Tally::bump>, Command<"SHOW", &Tally::show>>;
```

`FixedString<N>` — открытый массив символов с неявным конструктором из
литерала; `N` выводится из длины литерала (C++20, P0732). Повтор имени без
учёта регистра — `static_assert` «StaticRegistry: duplicate command name»;
тест `taskq_duplicate_command_fail` собирает пару «ACK» и «ack» и ждёт
именно этот текст.

Разбор и исполнение `StaticRegistry` не повторяет: внутри он строит обычный
`CommandRegistry`, и поведение двух реестров одинаково по построению. Рабочий
реестр остался динамическим: на этапе 15 команды сетевого протокола
регистрирует сетевой слой, и состав реестра при компиляции одной единицы
трансляции неизвестен.
