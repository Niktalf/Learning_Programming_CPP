# Этап 5: концепции, ranges, `<=>`, корутины

С этого этапа проект собирается под C++23. Вместе со стандартом пришли
`std::expected` (заменил `Result` этапа 3, см. конец `docs/errors.md`),
`std::print`, `std::format`, `std::generator` и `ranges::to`.

## Концепции

| Концепция | Где наложена | Что требует |
|---|---|---|
| `NameLike` | `contains`, `size`, `tasks_where` хранилища, `name_view` | `std::string`, `std::string_view` или строковый литерал |
| `QueuedTask` | параметр `BasicTaskStore<T>` | копирование, неброс перемещения, `id()` → целое, `key()` → ровно `TaskKey`, `set_sequence` |
| `Serializable` | `TaskKey` | `to_bytes()` → вектор байт и статический `from_bytes(span)` → ровно `T` |
| `std::predicate<const T&>` | `tasks_where` | вызываемый объект, возвращающий `bool` |

`NameLike` принимает литерал, но не `const char*`: концепция через
`std::convertible_to<T, std::string_view>` пропустила бы и указатель — без
длины и, возможно, нулевой.

`QueuedTask` проверяет тип результата `key()`: тип, у которого `key()`
возвращает приоритет числом, концепцию не проходит (`Concepts.QueuedTaskChecksResultTypes`).
Проверка «метод есть» пропустила бы его — и порядок выдачи сравнивал бы одни
приоритеты, без номера постановки.

### Диагностика: концепция против enable_if

| Программа | GCC 15, строк | Clang 20, строк | Куда указывает ошибка |
|---|---|---|---|
| `concept_name.cpp` — `store.contains(42)` | 27 | 31 | на вызов и на невыполненное `NameLike` с подсветкой всех ветвей дизъюнкции |
| `enable_if_name.cpp` — то же на `enable_if` | 20 | 7 | «no type named 'type' in `enable_if<false, bool>`» внутри `<type_traits>` |

На современных компиляторах объём у одноуровневой ошибки примерно одинаков,
а концепция бывает даже длиннее — она печатает каждое невыполненное условие.
Разница в содержании: с `enable_if` сообщение говорит, где сломалось; с
концепцией — что не выполнено и почему. Разрыв в объёме растёт с глубиной:
чем дальше от вызова неограниченный шаблон спотыкается, тем длиннее цепочка
`required from`.

## Оператор <=> для TaskKey

Здесь он важнее, чем в других вариантах: `TaskKey` определяет порядок выдачи
задач. Порядок — больший приоритет раньше, при равном — раньше поставленная;
«меньше» в смысле `<=>` значит «выдать раньше».

`PlainTaskKey{priority, seq}` с `= default` сравнивает поля по возрастанию, и
это неверно: задача с приоритетом 0 «меньше» задачи с приоритетом 9 и
выдавалась бы первой. Тест `TaskKey.DefaultOrderIsWrongForPriority` фиксирует
ошибку, которую `= default` делает молча.

`TaskKey` написан руками:

```cpp
std::strong_ordering operator<=>(const TaskKey& other) const noexcept {
    if (const auto order = other.priority <=> priority; order != 0) {   // по убыванию
        return order;
    }
    return seq <=> other.seq;                                           // по возрастанию
}
```

Операнды приоритета переставлены — `other` слева. Именно здесь чаще всего
ошибаются, и ошибка видна только на смешанных приоритетах. Поэтому главный
тест — `Service.PollRespectsPriorityThenOrder`: пять задач с приоритетами
0, 9, 5, 9, 0 выдаются в порядке 9, 9, 5, 0, 0, а равные — в порядке
постановки.

Поле `requester` в сравнении не участвует, и `operator==` пришлось объявить
отдельно: из написанного руками `<=>` он не выводится.

`POLL` теперь выдаёт задачу с наименьшим ключом, а не первую поставленную.
Очередь остаётся вектором в порядке постановки, и следующая задача ищется
линейно — `min_element` по ключу. На этапе 7 вектор сменит приоритетная
очередь, и ключ станет её порядком. Номер постановки выдаёт хранилище, в том
числе при возврате аренды: вернувшаяся задача встаёт за равными по приоритету
(`Service.ReleasedTaskGoesBehindItsPriorityPeers`).

## LIST через ranges

`LIST <queue> [prio>=N] [type=K] [limit=N]` — задачи, ждущие в очереди, в
порядке постановки. Аргументы именованные, в любом порядке. Реализация —
`BasicTaskStore::tasks_where`:

```cpp
auto selected = tasks
              | std::views::filter([min_priority](const T& t) { return t.priority() >= min_priority; })
              | std::views::filter([&](const T& t) { return predicate(t); })
              | std::views::take(bounded);
```

Ленивость доказана счётчиком (`List.PipelineIsLazy`): на тысяче задач при
пределе 10 предикат вызван 11 раз, а не тысячу. Одиннадцатый — продвижение
`filter` после последнего элемента. `List.PriorityFilterRunsFirst` показывает,
что второй фильтр видит только то, что пропустил первый.

Предел обрезается по размеру очереди до `take`: `take` принимает знаковую
разность итераторов, и `size_t` больше `PTRDIFF_MAX` превратился бы в
отрицательное число. Эту ошибку нашёл фаззер варианта B на таком же
конвейере; здесь она закрыта сразу (`List.HugeLimitIsClampedNotNegative`), а
фаззер этапа 3 теперь гоняет и `LIST` с числами на краю диапазона.

Материализация — обычным циклом, а не `ranges::to`: тот для прямого диапазона
проходит его дважды, и предикаты вызывались бы почти вдвое чаще. Возвращаются
ссылки внутрь очереди: пока результат жив, очередь нельзя менять.

## Висячий диапазон

`tests/compile_fail/dangling_range.cpp`: `std::ranges::find` над временным
вектором возвращает `std::ranges::dangling`, и обращение через него не
компилируется. Защита держится на объявлении `borrowed_range`, а не на анализе
времени жизни: над временным `string_view` тот же `find` вернёт обычный
итератор — и это корректно, данные принадлежат не виду.

## Звёздочка: генератор

`BasicTaskStore::tasks_lazily(queue)` — `std::generator<const T&>`. Тест
`Generator.EarlyExitDestroysCoroutineLocals` прерывает цикл `break`: пока
генератор жив, корутина приостановлена и её локальный объект жив; как только
генератор разрушен, кадр корутины уничтожается в точке приостановки, и
локальный объект разрушается — RAII работает и внутри корутины. Плата — кадр
корутины в куче.
