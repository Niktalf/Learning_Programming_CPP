# Домашнее задание этапа 5: модули

## Что сделано

Строгая проверка UTF-8 из `src/validate.cpp` вынесена в именованный модуль
`chat.utf8` (`modules/chat.utf8.cppm`), и программа `chat_modules_demo`
импортирует его. Вспомогательная функция `in_range` в модуле не
экспортируется — и снаружи её не видно вовсе: анонимное пространство имён для
этого больше не нужно. Эксперимент включается явно:

```bash
cmake -B build-modules -G Ninja -DCHAT_MODULES=ON
cmake --build build-modules --target chat_modules_demo
./build-modules/chat_modules_demo
```

Собирается и работает с GCC 15.2 и с Clang 20.1 на CMake 3.28 и Ninja 1.11.

## Почему модуль один, а не весь проект

Препятствия, найденные по ходу, — по порядку, в котором они встречаются.

**Генератор сборки.** CMake 3.28 поддерживает модули только с Ninja и с
Visual Studio 17.4 и новее. С `-G "Unix Makefiles"` конфигурация падает сразу:
«modules are not supported by this generator». Студенту, привыкшему к
Makefiles, придётся сменить генератор.

**Сканирование зависимостей.** Порядок компиляции перестаёт быть
произвольным: интерфейс модуля надо собрать до тех, кто его импортирует.
CMake для этого сканирует каждый исходник (P1689). По умолчанию с C++20 и
новее сканирование включено для всех целей — это замедляет сборку и
добавляет к каждой команде флаги модулей. В проекте оно выключено глобально
(`CMAKE_CXX_SCAN_FOR_MODULES OFF`) и включено только для двух целей
эксперимента.

**`import std`.** Импорт стандартной библиотеки модулем требует CMake 3.30 с
экспериментальным флагом `CMAKE_EXPERIMENTAL_CXX_IMPORT_STD`. Без поддержки
системы сборки GCC 15 отвечает «failed to read compiled module: gcm.cache/std.gcm»
— модуль стандартной библиотеки надо сначала собрать отдельно. Поэтому
стандартные заголовки подключены в глобальном фрагменте модуля, через
`#include`.

**Смешивание заголовков и `import`.** В потребителе важен порядок: сначала
`#include <print>`, потом `import chat.utf8`. Обратный порядок с GCC 15 даёт
десятки ошибок вида «template definition of non-template
`std::integral_constant<...>::value`»: определения из `<type_traits>`,
пришедшие через модуль, конфликтуют с повторным разбором того же заголовка.
Это главное препятствие для перевода всего проекта: GoogleTest, nlohmann и
прочие сторонние библиотеки ещё долго будут заголовками, и каждая единица
трансляции, где они встречаются с модулями, становится полем для таких
конфликтов.

**Шаблоны.** Ядро проекта — шаблоны: `BasicChatStore`, концепции. Экспорт шаблона из модуля работает, но его определение всё равно
целиком лежит в интерфейсе модуля, и выигрыш во времени сборки, ради которого
модули затевались, для такого кода меньше, чем для обычных функций.

**Несовместимость компиляторов.** Скомпилированный интерфейс модуля (BMI у
GCC — `.gcm`, у Clang — `.pcm`) привязан к компилятору, его версии и флагам.
Собрать модуль GCC и импортировать его в Clang нельзя; в проекте, где оба
компилятора — обязательная проверка, каждый собирает модули сам.

**Инструменты.** Поддержка модулей в clangd пока экспериментальная и
включается ключом `--experimental-modules-support`; без него редактор может
подсвечивать `import chat.utf8` как ошибку, хотя сборка проходит.

## Итог

Один модуль без шаблонов, импортируемый в одну программу, работает на обоих
компиляторах. Перевести на модули ядро проекта мешают в первую очередь
конфликты с заголовками сторонних библиотек и отсутствие `import std` в
доступной версии CMake; во вторую — то, что ядро состоит из шаблонов. К этому
вопросу имеет смысл вернуться, когда `import std` станет штатным, а
GoogleTest — доступен модулем.
