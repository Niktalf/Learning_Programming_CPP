# Этап 7: итератор истории, emplace, operator[] и инвалидация

## Итератор кольцевого буфера

`RingBuffer<T>::iterator` и `const_iterator` (`include/chat/ring_buffer.hpp`)
— двунаправленные итераторы по истории от старого сообщения к новому.

```cpp
static_assert(std::forward_iterator<Ring::iterator>);
static_assert(std::bidirectional_iterator<Ring::const_iterator>);
static_assert(std::ranges::bidirectional_range<const Ring>);
```

Итератор хранит указатель на буфер и **логический** индекс — 0 у самого
старого сообщения. Физический индекс в векторе получается при разыменовании:
`head + i`, и если вышло за размер — минус размер. Так обход проходит точку
переноса — конец вектора — сам собой, и для этого в итераторе нет ни одной
отдельной ветки. Тест `RingBuffer.IterationCrossesTheWrapPoint` проверяет
каждое число добавлений от 0 до 13 в кольцо на четыре.

Почему двунаправленный, а не только прямой: история читается с конца.
`history_where` строит конвейер `enumerate | reverse | filter | take`, и
`views::reverse` требует `operator--`. Комментарий этапа 5 это и
предсказывал: «на этапе 7 история переедет в кольцевой буфер, и его
итератор придётся сделать двунаправленным, иначе конвейер не соберётся».
Произвольный доступ был бы возможен — индекс есть, — но в проекте не нужен.

Что понадобилось:

| Член | Зачем |
|---|---|
| пять типов-членов | `iterator_category`, `value_type`, `reference`, `pointer`, `difference_type` смотрят `iterator_traits` и концепции |
| конструктор по умолчанию | требование `forward_iterator` |
| явные `= default` копирование и перемещение | см. ниже — без них итератор не копируется |
| преобразование `iterator` → `const_iterator` | как у стандартных контейнеров, только в одну сторону |
| `++`, `--` в обеих формах | постфиксные возвращают копию до сдвига |
| `operator==` | `= default`; `!=` C++20 выводит сам |

### Ловушка: конструктор, который выключил копирование

Преобразование изменяемого итератора в константный записано так:

```cpp
Cursor(const Cursor<false>& other) requires Const;
```

У `Cursor<true>` это обычный преобразующий конструктор. У `Cursor<false>` у
него сигнатура копирующего конструктора, и хотя `requires` его выключает,
объявлен он пользователем. Пользовательский копирующий конструктор отменяет
неявный перемещающий, а выключенный — не заменяет копирующий. Итератор
оказался неперемещаемым, и `static_assert(std::forward_iterator<...>)` не
прошёл: диагностика GCC привела к `movable<_Iter>` и
`is_constructible_v<Cursor<false>, Cursor<false>>`. Исправление — явные
`= default` для всех четырёх операций. Это ровно та ситуация, для которой
`static_assert` на концепцию и нужен: без него ошибка всплыла бы в первом
алгоритме, который скопирует итератор.

После итератора история работает в range-based for, в классических
алгоритмах (`std::accumulate`, `std::count_if`, `std::find`,
`std::distance`) и в ranges (`views::reverse`, `views::enumerate`,
`ranges::is_sorted`): `tests/test_ring_buffer.cpp`.

## Звёздочка: страж

`ring.from_oldest()` — те же элементы, но конец — отдельный тип
`RingBuffer::End`, а не второй итератор. Итератор сравнивается со стражем
сам: конец — когда логический индекс дошёл до размера. Диапазон —
`std::ranges::subrange<const_iterator, End>`, двунаправленный, но не
`common_range`.

Что это меняет на практике — проверено тестом
`RingBuffer.SentinelRangeWorksWithRangesAlgorithms`:

- range-based for и алгоритмы ranges (`ranges::count_if`,
  `ranges::distance`) принимают страж;
- классические алгоритмы — `std::accumulate(first, last)` — требуют пару
  итераторов одного типа, и с `from_oldest()` они не соберутся. Поэтому
  `begin()` и `end()` самого буфера остались парными: история должна
  работать в алгоритмах STL по постановке.

Зачем страж вообще: на этапе 13 разбор потока байтов из сокета — диапазон,
конец которого заранее неизвестен. «Конец» там — не позиция, а условие, и
страж выражает это прямо.

## emplace против push, try_emplace против insert

`tests/test_emplace.cpp` на типе `Traced`, который пишет в журнал каждый
вызов конструктора:

| Вызов | Что происходит |
|---|---|
| `v.push_back(Traced("x"))` | construct, move |
| `v.emplace_back("x")` | construct — на месте |
| `v.emplace_back(variable)` | construct, copy — копию lvalue убирает только `std::move` |
| `m.insert({"k", Traced("new")})` при занятом ключе | значение построено, перенесено в пару и выброшено |
| `m.try_emplace("k", "new")` при занятом ключе | ничего |
| `m.try_emplace("k", "x")` для нового | construct — один раз |
| `m["k"] = Traced("x")` | construct, default, move-assign |

### Что исправлено в коде

- **`join` строил строку ключа на каждый вход в комнату.** Ключ
  `try_emplace` у `std::map<std::string, …>` — `std::string`, и
  `try_emplace(std::string(room), …)` создавал строку и для существующей
  комнаты, чтобы тут же её выбросить. Теперь сначала `find` по
  `string_view`, и только для новой комнаты — `try_emplace`.
  Разнородный `try_emplace` появится в C++26.
- **`members` растил вектор удвоением** и при каждом росте переносил уже
  собранные `shared_ptr`. Теперь `reserve` по размеру состава.
- **Комната строится только при вставке.** У `Room` появился конструктор от
  ёмкости истории, и `try_emplace(name, capacity)` передаёт ёмкость ему —
  для существующей комнаты ни `Room`, ни её буфер не строятся.

## Ловушка operator[]

```bash
grep -rn '\]\s*=' include src
grep -rn 'operator\[\]' include src
```

Ни одного `operator[]` на ассоциативном контейнере в рабочем коде нет. Все
операции хранилища ищут комнату через `find` и на отсутствующую отвечают
`UnknownRoomError` или пустым `optional`. Комнату создают ровно два места,
и оба намеренно: `create_room` и `join` — войти в новую комнату и значит её
завести. Если бы `/msg #genral привет` с опечаткой шёл через
`rooms_[name]`, он молча создал бы комнату `#genral`, в которой никого нет,
и сообщение ушло бы в пустоту. Тест `Commands.MessageRequiresMembership`
проверяет обратное: `/msg #absent hi` — `UnknownRoomError`, и комнаты
`#absent` после этого нет.

`operator[]` у кольцевого буфера — другое дело: это доступ по индексу, как
у vector, и он ничего не создаёт.

## Домашнее задание: удаление внутри обхода

`tools/invalidation_demo.cpp` — обход состава комнаты
(`std::set<std::weak_ptr<User>, std::owner_less<>>`, как
`BasicChatStore::Members`) с удалением ушедших. Ошибка — `++it` после
`erase(it)`.

### Санитайзер адресов молчит

```
$ ./chat_invalidation_demo           # сборка с -fsanitize=address
members left: 8
```

Программа «работает» и даже выдаёт правильное число. Причина — где живёт
код инкремента. Итератор `set` сдвигается функцией `_Rb_tree_increment`, а
она определена не в заголовке, а в `libstdc++.so`. Библиотека собрана без
санитайзера, и чтение освобождённого узла происходит в коде, который
санитайзер не видит. (Для контраста: у `unordered_map` инкремент — inline
в заголовке, и там санитайзер ту же ошибку ловит.)

### valgrind видит

инструментированным кодом:

### Отладочный режим видит

```
$ ./chat_invalidation_debug          # -D_GLIBCXX_DEBUG
.../debug/safe_iterator.h:392:
    gnu_debug::_Safe_iterator<...>::operator++()
    [with _Iterator = std::_Rb_tree_const_iterator<std::weak_ptr<chat::User> >; ...]

```

Цель `chat_invalidation_debug` собирается всегда, тест ctest
`chat_invalidation_detected` проверяет это сообщение. С `chat_core` она не
связывается: отладочный режим меняет устройство контейнеров, и смешивать
его с библиотекой, собранной без него, нельзя.

Вывод: «санитайзер ничего не нашёл» — не доказательство. Он видит только
инструментированный код.

### Исправление

```cpp
for (auto it = members.begin(); it != members.end();) {
    if (it->expired()) {
        it = members.erase(it);
    } else {
        ++it;
    }
}
```

`BasicChatStore::purge` с этапа 4 был написан так; с этапа 7 он — одна
строка `std::erase_if(members, ...)` из C++20. Тесты —
`tests/test_invalidation.cpp`.

### Какие операции делают итераторы истории недействительными

Итератор кольца — буфер и логический индекс, а не указатель на элемент, и
правила у него свои. Все они — определённое поведение, и каждое проверено
тестом в `tests/test_ring_buffer.cpp`:

| Операция | Итераторы | Ссылки на элементы |
|---|---|---|
| `push_back`, буфер не полон, без перевыделения | действительны; бывший `end()` теперь указывает на новое сообщение | действительны |
| `push_back`, буфер не полон, с перевыделением | действительны — индекс тот же | **недействительны**: элементы переехали |
| `push_back`, буфер полон (вытеснение) | действительны, но **смотрят на соседнее** сообщение: тот же индекс теперь означает следующее | ссылка на самое старое теперь ссылается на новое — его записали поверх |
| `reserve_one_more` | действительны | недействительны, если было перевыделение |

Вывод для чата тот же, что для любого контейнера: обход истории нельзя
смешивать с добавлением. Ни висячих указателей, ни падения не будет — будет
неверный результат: итератор молча сдвинется на одно сообщение. Поэтому
`history_where` собирает результат до того, как кто-то напишет в комнату, и
возвращает его копией номеров и ссылок, которые живут, пока комната не
меняется, — тот же урок, что со `string_view` на этапе 2.
