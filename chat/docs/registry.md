# Этап 6: реестр команд

До этапа 6 команда проходила три места: структура в `command.hpp`, ветка в
`parse` (и вторая — в `try_parse`) и ветка в `std::visit` исполнителя.
Добавить команду — поправить четыре места и не забыть ни одного. Реестр
сводит это к одной строке:

```cpp
table.register_command("/kick", kick);
```

и функции-обработчику рядом:

```cpp
Response kick(Context& call, RoomName room, Nick target);
```

Арность, разрезание строки, проверка аргументов, подсказка об использовании
и контекст для цепочки исключений выводятся из сигнатуры. Обработчик получает
уже проверенные аргументы и ни одной проверки формы не содержит.

Файлы: `include/chat/function_traits.hpp`, `include/chat/convert.hpp`,
`include/chat/registry.hpp`, `src/commands.cpp`. Старые `command.hpp`,
`parser.*` и `executor.*` удалены.

## Как реестр узнаёт сигнатуру

`function_traits<F>` — шаблон с частичными специализациями для указателя на
функцию, типа функции, указателя на метод (`const`, не `const`, `noexcept`)
и класса с `operator()`. Последняя специализация ограничена
`requires { &F::operator(); }` и сводится к специализации для указателя на
метод — так лямбда и функтор получают сигнатуру своего `operator()`. У
обобщённой лямбды `&F::operator()` не вычисляется, основной шаблон пуст, и
реестр отвергает такой обработчик первым требованием концепции.

## Типы аргументов

Аргументы-строки в чате не равноправны: имя комнаты, ник, текст сообщения
проверяются разными правилами. До реестра каждая ветка `parse` вызывала
нужную проверку сама. Теперь проверка привязана к типу:

| Тип | Что это | Проверка | В подсказке |
|---|---|---|---|
| `RoomName` | имя комнаты | `room_name_problem` | `<#room>` |
| `RoomList` | `#a,#b,#c` для `/msg` | каждое имя, без повторов | `<#room[,#room...]>` |
| `Nick` | ник | `nick_problem` | `<nick>` |
| `Text` | один токен текста — тема | `text_problem` | `<"text">` |
| `Tail` | весь остаток строки — текст `/msg` | `text_problem` | `<text...>` |
| `std::string_view` | слово как есть | — | `<word>` |
| числа | индекс, предел, шаг | `from_chars` до конца токена | `<number>` |

`std::optional<T>` — необязательный аргумент, в подсказке `[...]`.

Обработчик с параметром `RoomName` не может получить непроверенное имя
комнаты: проверка случилась при разборе, и тип это фиксирует. Добавить новую
команду с комнатой — значит просто написать `RoomName` в сигнатуре.

`convert<T>` — один шаблон с ветками `if constexpr` по этим типам. Порядок
веток существен: специальное раньше общего. Для беззнакового числа сообщение
точнее: «not a non-negative number: -1» — номер сообщения и предел не бывают
отрицательными.

`static_assert(false)` в последней ветке законен с C++23 (P2593); до него
писали зависимое выражение вроде `sizeof(T) == 0`.

## `Tail`: остаток строки

У `/msg` текст — весь остаток строки после списка комнат, с пробелами и
кавычками как есть: `/msg #general он сказал "привет` — не ошибка
незакрытой кавычки. Лексер это умеет с этапа 2: `tokenize(line, n)` после
`n - 1` токенов отдаёт остаток одним куском. Вопрос — откуда реестру знать
`n`.

Из сигнатуры. Если последний параметр обработчика — `Tail`, строка режется
на глагол, обязательные аргументы и остаток: `n = число параметров + 1`.
Иначе — на токены целиком. Сначала реестр берёт только глагол
(`tokenize(line, 2)`), находит команду, и уже она решает, как резать
остаток.

Отсюда ограничение формы: `Tail` — только последним и не вместе с
необязательными. Если бы `/msg` выглядела как `<rooms> [number] <text...>`,
строку «/msg #a 5 штук» нельзя было бы разрезать однозначно. Нарушение
формы — ошибка компиляции при регистрации (`detail::Shape::valid`).
`std::optional<Tail>` концепция `Argument` тоже не пропускает.

## Подсказка вместо «expects 2 arguments»

Ошибка арности — `ParseError` с подсказкой, собранной из типов параметров:

```
ERR usage: /history <#room> [number] [nick]
```

Ошибка в самом аргументе — `ParseError` из `convert` с причиной и
неразобранным токеном. Реестр приклеивает к ней ту же подсказку тем же
`std::throw_with_nested`, которым этап 3 приклеивал контекст исполнения:

```
ERR not a non-negative number: x (usage: /history <#room> [number] [nick])
```

Граница `handle` разворачивает цепочку как раньше: причина — по корню,
звенья — в скобках. Ни одной новой строки в `handle`.

Подсказку нельзя забыть обновить: она выводится из той же сигнатуры, по
которой разбираются аргументы, и разойтись с ней не может. Цена — имена
вместо смысла: `<number>`, а не `<index>`. Имени параметра функции в типе
нет, и вывести его неоткуда.

## `if constexpr` против `enable_if`

`include/chat/legacy_convert.hpp` — `convert` для строки, числа и
`RoomName` на трёх перегрузках с `std::enable_if`. Сравнение — в
комментарии в начале файла; коротко:

| | `if constexpr` + концепция | `enable_if` |
|---|---|---|
| Где правило выбора | в одном месте, ветки по порядку | в условии каждой перегрузки |
| Добавить случай | одна ветка | новая перегрузка и исключение её во всех прочих |
| Неподдерживаемый тип | одна строка с именем концепции | «no matching function» и по примечанию на перегрузку |
| Порядок предпочтения | порядок веток | нет: условия обязаны быть взаимоисключающими |

Тест `Convert.LegacyAgreesWithModern` проверяет, что обе версии ведут себя
одинаково на одних и тех же токенах.

## Концепция `CommandHandler`

Пять требований, у каждого своё имя: `HasSignature`, `ReturnsResponse`,
`TakesContextFirst`, `ArgumentsSupported`, `ArgumentOrderValid`.
Конъюнкция проверяется слева направо и останавливается на первом
невыполненном. Именованные требования — ради диагностики: на
`tests/compile_fail/bad_handler.cpp` (имя комнаты как `const char*`) GCC 15
пишет

```
required for the satisfaction of 'ArgumentsSupported<F>'
    [with F = chat::Response (*)(chat::Context&, const char*)]
```

— 25 строк вывода вместе с командой компиляции, и первая ошибка указывает
на строку `register_command` в коде студента. Тест
`chat_bad_handler_fail` проверяет и отказ сборки, и имя требования в выводе.

## Контекст исполнения

Обработчик получает `Context&` — хранилище, сессию и необязательный журнал:

```cpp
struct Context {
    ChatStore& store;
    Session& session;
    AppendOnlyLog* journal = nullptr;
};
```

Журнал — указатель, потому что его может не быть. Указатель не владеющий:
журналом владеет `Server`. До реестра сервер сам решал, писать ли в журнал,
проверяя `std::get_if<MsgCommand>`. Без `variant` эта проверка невозможна,
и писать стал обработчик `/msg` — единственный, кто знает, что именно
отправлено.

## Что поменялось в поведении

- Ошибки арности — подсказка «usage: …» вместо «/join expects 1 argument».
- У `ParseError` от аргумента `input` — сам токен, а не вся строка.
- `/topic`: уведомление публикуется до смены темы. `post` может бросить, а
  присваивание перемещением — нет; в прежнем порядке бросок оставлял тему
  сменённой без следа в истории.

## Домашнее задание: `/kick`, `/rooms`, `/nick`

`/nick` появилась на этапе 3 и переехала в реестр одной строкой, как и
остальные восемь. Новые — `/kick` и `/rooms`; ни одна не потребовала правок
вне `src/commands.cpp`, кроме новой операции хранилища для `/kick`.

`/kick #room nick` — это не `leave`, а затем `post`, а одна операция
`ChatStore::kick`. Если бы `post` бросил после `leave`, участник был бы
исключён без следа в истории. `kick` делает всё, что может бросить, — поиск,
проверки, запас ёмкости истории, — до первого изменения, а затем `erase` и
`push_back` в запасённую ёмкость, которые не бросают. На этапе 11 это ещё и
один захват мьютекса: между исключением и уведомлением никто не вклинится.

`/rooms` перечисляет комнаты по алфавиту с числом живых участников. Порядок
— свойство `std::map`, на котором лежат комнаты; на этапе 7 это станет
аргументом в выборе между `map` и `unordered_map`.

## Звёздочка: `StaticRegistry`

`include/chat/static_registry.hpp`. Имя команды — параметр шаблона:

```cpp
using Commands = StaticRegistry<Tally, Command<"/bump", bump>, Command<"/show", show>>;
```

`FixedString<N>` — открытый массив символов с неявным конструктором из
литерала; `N` выводится из длины литерала (C++20, P0732). Повтор имени без
учёта регистра — `static_assert` «StaticRegistry: duplicate command name»;
тест `chat_duplicate_command_fail` собирает пару «/bump» и «/BUMP» и ждёт
именно этот текст. У обычного реестра тот же повтор — `std::logic_error`
при запуске.

Разбор и исполнение `StaticRegistry` не повторяет: внутри он строит обычный
`CommandRegistry`, и поведение двух реестров одинаково по построению.

Рабочий реестр чата остался динамическим: на этапе 15 команды сетевого
протокола регистрирует сетевой слой, на этапе 16 маршруты — HTTP-слой, и
состав реестра при компиляции одной единицы трансляции неизвестен.
