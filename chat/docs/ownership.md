# Владение ресурсами

Этап 4. Ни одного `new` и `delete` в рабочем коде: всё, что выделяется, кому-то
принадлежит, и освобождается деструктором владельца.

## Кто чем владеет

| Ресурс | Владелец | Вид владения | Почему так |
|---|---|---|---|
| сообщение (`IMessage`) | история комнаты | `unique_ptr` в `vector` | владелец один — комната |
| пользователь (`User`) | реестр в `ChatStore` | `shared_ptr` | на этапе 15 владельцем станет и сетевая сессия |
| участник комнаты | комната | `weak_ptr` | комната наблюдает, но не удерживает ушедшего |
| участники на время рассылки | вызывающий `members()` | `shared_ptr` из `lock()` | получатель не исчезнет посреди операции |
| файл журнала | `AppendOnlyLog` в `Server` | поле `std::ofstream` | RAII |
| хранилище, журнал | `Server` | поля | всё освобождается деструктором сервера |

`shared_ptr` в проекте ровно на пользователей, и это оправдано: на этапе 15
пользователь принадлежит и реестру, и своей сессии. Сообщением владеет одна
комната — `unique_ptr`.

## Полиморфные сообщения

`IMessage` — абстрактная база с виртуальным деструктором и общими полями
(автор, время); `TextMessage`, `SystemMessage`, `ReactionMessage` — наследники.
Комната хранит `std::vector<std::unique_ptr<IMessage>>`. Без `virtual` удаление
через `unique_ptr<IMessage>` — неопределённое поведение; тест
`Message.DeletingThroughBaseRunsDerivedDestructor` проверяет это счётчиком.

Самая частая поломка этапа — сильная гарантия рассылки. На этапе 3 копии
сообщения для каждой комнаты делались копированием, а `unique_ptr` не
копируется: без исправления `post_many` просто не собирается. Исправление —
виртуальный `clone` и функция `duplicate`: для `MessagePtr` она вызывает
`clone`, для копируемых тестовых типов — обычное копирование. Хранилище
осталось шаблоном, тесты этапа 3 прошли без изменений, а
`Guarantee.PostManyWithPolymorphicMessages` повторяет перебор точек броска на
настоящем `ChatStore` с сообщением, чей `clone` бросает.

Фиксация рассылки по-прежнему переносит копии перемещением: перемещение
`unique_ptr` не бросает, и `static_assert` в `post_many` это проверяет.

## Участники на weak_ptr

Реестр пользователей владеет через `shared_ptr`, комната хранит
`std::set<std::weak_ptr<User>, std::owner_less<>>`. `owner_less` сравнивает
`weak_ptr` по контрольному блоку, а не по значению указателя, и сравнение
остаётся корректным, даже когда объект уже уничтожен: истёкший `weak_ptr`
можно найти в множестве и удалить.

Тест `Members.RoomDoesNotKeepDepartedUserAlive`: после удаления пользователя
из реестра `expired()` даёт `true`, `lock()` — пустой указатель, комната
перестаёт считать его участником. `Server::logout` — то, что на этапе 15 сделает
отключение клиента; комнаты об этом не узнают и не должны.

На время рассылки участников надо удержать: `members()` возвращает
`shared_ptr` из `lock()`, и пока вызывающий держит результат, получатель не
исчезнет посреди операции (`Members.LockedMembersSurviveDeparture`). `weak_ptr`
не запрещает владеть — он запрещает владеть постоянно.

Истёкшие записи — тоже утечка, только медленная: составы растут на каждого
ушедшего. `join` и `leave` чистят свою комнату, `purge_departed` — все сразу.
К тому же `make_shared` кладёт пользователя и контрольный блок в одну
аллокацию: деструктор `User` вызывается сразу, а память блока освобождается,
только когда умрёт и последний `weak_ptr` — когда очистка удалит запись.

Попутно упростилась смена ника. На этапе 3 ник был строкой в составе каждой
комнаты, и `/nick` менял все составы. Теперь комнаты хранят ссылку на объект,
и `rename` меняет одно поле одного объекта и ключ реестра — переносом узла
`extract`/`insert` из C++17, без выделения памяти. Ни одна комната не меняется
(`ChatStore.RenameTouchesOneObjectAndNoRoom`). И вернувшийся с тем же ником
пользователь — другой объект: комната не путает его с прежним
(`Members.SameNickAfterReturnIsADifferentUser`).

## Журнал сообщений

`AppendOnlyLog` открывает файл в конструкторе и закрывает в деструкторе;
`open` и `close` в интерфейсе нет. Копирование запрещено, перемещение
разрешено. `chat_cli alice --log=chat.log` дописывает каждое отправленное
сообщение строкой «комнаты, автор, текст» через табуляцию — архив, как логи
IRC-канала.

Закрытие доказано подсчётом открытых дескрипторов процесса: тест
`Log.ClosedOnException` бросает исключение посреди области видимости журнала
и проверяет, что дескриптор закрыт, а записанное до броска — на диске.
`Server.FailedConstructionLeaksNothing` проверяет то же для броска из
конструктора сервера: деструктор не вызовется, но поля разрушатся.

## Попутная находка: временный объект в range-for

Первая версия фаззера проверяла участников так:

```cpp
for (const auto& user : *store.members(room)) { ... }
```

и санитайзер адресов остановил её с `stack-use-after-scope`. `members`
возвращает `optional` по значению, `*` даёт ссылку внутрь него, а время жизни
временного объекта в заголовке range-for продлевается только для самого
выражения — не для того, во что ссылается результат `operator*`. Optional
уничтожается до первой итерации. Это та же висячая ссылка, что на этапе 2,
только спрятанная в синтаксис; в C++23 правило изменили (P2718). Исправление —
сначала в переменную.

## Звёздочка: цикл из shared_ptr

`tools/cycle.hpp`: пользователь держит комнаты, в которые вошёл, комната держит
участников. Вид ссылки от комнаты к участникам — параметр шаблона.

- `chat_cycle_demo` — комната держит участников через `weak_ptr`: после ухода
  обоих живых объектов 0.
- `chat_cycle_leak` — тот же код с `CHAT_LEAKING_CYCLE`, ссылка `shared_ptr`:
  живых объектов 2, санитайзер адресов сообщает об утечке 176 байт в четырёх
  блоках. В обычную сборку не входит.

Все блоки LeakSanitizer помечает как косвенные утечки — почерк цикла: каждый
блок указан другим утёкшим, прямой утечки нет. Тесты `Cycle.*` показывают то
же счётчиком живых объектов и в конце разрывают цикл руками.

Правило: обратная ссылка почти всегда должна быть `weak_ptr`, и в модели
«контейнер — элемент» `weak_ptr` смотрит туда, где элемент может исчезнуть
раньше контейнера. Настоящее хранилище устроено именно так.

## Домашнее задание: OwningBuffer на unique_ptr<char[]>

| | Этап 1, `char*` | Этап 4, `unique_ptr<char[]>` |
|---|---|---|
| деструктор | написан | исчез |
| копирующий конструктор | написан | остался |
| копирующее присваивание | написано (copy-and-swap) | одно присваивание по значению |
| перемещающее присваивание | написано | на оба случая |
| перемещающий конструктор | написан | остался — см. ниже |
| строк кода без комментариев (`.hpp` + `.cpp`) | 63 | 54 |

Деструктор исчез: `unique_ptr<char[]>` сам вызовет `delete[]`. Два
присваивания слились в одно, принимающее параметр по значению.

Копирующий конструктор остался, потому что `unique_ptr` не копируется.
Перемещающий остался, хотя `unique_ptr` перемещается сам: инвариант класса
связывает два поля — нет буфера, значит нулевая длина. Сгенерированное
перемещение оставило бы в источнике прежний `size_` при пустом указателе.
Правило нуля работает, когда каждое поле само отвечает за свой инвариант.

`make_unique<char[]>(n)` обнуляет память, `new char[n]` — нет; в C++20 для
этого есть `make_unique_for_overwrite`, на C++17 приходится платить.
