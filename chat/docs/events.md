# Этап 10. Доменные события

## Что публикуется

| Событие | Когда | Поля |
|---|---|---|
| `UserJoined` | `/join` нового участника | комната, ник |
| `UserLeft` | `/leave`, `/kick`, выход из чата (`logout`) — по событию на каждую комнату | комната, ник |
| `MessagePosted` | `/msg` (по событию на комнату рассылки), уведомления о входе, выходе, исключении | комната, автор, текст, вид (text, notice, reaction), номер сообщения |

Порядок событий одной команды — порядок фактов: `/join` — сначала `UserJoined`,
потом уведомление «* alice joined»; `/kick` — `UserLeft`, потом уведомление.

Чтения (`/who`, `/history`, `/rooms`, `/since`…) событий не дают. Неудачная
команда событий не даёт тоже: хранилище готовит события вместе с остальной
подготовкой операции, до первого изменения, и если подготовка бросила, их нет.
Рассылка `/msg #a,#b` — одно сообщение в двух комнатах: два события с одним и
тем же номером сообщения, и либо оба, либо ни одного.

`/react` и `/topic` событий не дают: в постановке этапа три события, и
изменения существующих сообщений и тем в них не входят. Добавить событие —
альтернатива в `DomainEvent`; адаптер и потребитель без обработчика для неё не
скомпилируются (`std::visit` с `overloaded`).

## Где события рождаются и где публикуются

```
Server::handle ─► обработчик ─► ChatStore::post_many ─► prepare_events (копии строк, место в очереди)
                                                     ─► подготовка рассылки
                                                     ─► фиксация (noexcept)
                                                     ─► emit (noexcept)
               ─► publish_events: take_events → IEventPublisher::publish
```

Хранилище события копит, но не публикует; публикует `Server`, когда команда
выполнена. На этапе 11 у хранилища появится мьютекс, и события будут
забираться под ним, а отправляться — после. Держать мьютекс, пока событие
уходит в брокер, значит остановить весь чат на время сетевой операции.

## Ключ сообщения

Ключ сообщения Kafka — имя комнаты.

Kafka хранит порядок только внутри партиции, а партиция выбирается по хешу
ключа. Поэтому все события одной комнаты ложатся в одну партицию и приходят
подписчику в том порядке, в каком произошли: вход участника — раньше его первого
сообщения, сообщения — в порядке ленты. Это проверяет сквозной тест
`Kafka.EventsOfOneRoomKeepTheirOrder`: у каждой комнаты одна партиция, вход bob в
`#a` прочитан раньше его сообщения, номера событий комнаты идут подряд.

Чего ключ не даёт — порядка между комнатами. Его в топике с тремя партициями
нет вообще, и он не нужен: ленты разных комнат независимы. Рассылка в `#a` и
`#b` может прийти подписчику в `#b` раньше, чем в `#a`.

Ключ-ник был бы содержательной ошибкой: упорядоченными оказались бы события
одного пользователя, а лента комнаты, где пишут двое, могла бы перемешаться —
ответ раньше вопроса. Работало бы на демонстрации с одним пользователем и
ломалось бы при втором.

## Тело сообщения

Строка, поля через табуляцию (`event_wire.hpp`):

```
3fa1…07	12	posted	#general	alice	text	41	hello
3fa1…07	13	joined	#general	bob
```

Первые два поля — издатель и номер события в комнате. Издатель — случайный
идентификатор процесса-сервера; номер — счётчик событий комнаты у этого
издателя, 1, 2, 3… Тройка «издатель, комната, номер» однозначно называет
событие: по ней потребитель узнаёт повтор, а по разрыву в номерах — пропуск.
Номер сообщения в чате (`MessageId::seq`) для этого не годится: он общий на
весь чат, и в ленте одной комнаты идёт с разрывами.

Табуляция, перевод строки и обратная косая черта в полях экранируются. Текст,
а не JSON: `lab-stand events` показывает тело как есть.

## Домашнее задание: брокер недоступен

| Выбор | Что происходит при лежащем брокере |
|---|---|
| Блокироваться, пока брокер не примет | Отказ брокера становится отказом чата: никто не может написать |
| Копить без предела | Отказ брокера становится исчерпанием памяти |
| Терять события | Чат работает, подписчики получают ленту с дырами |

**Выбрано: копить с пределом, при переполнении — терять и показывать дыру.**

1. `send` обёртки не блокируется и не ходит в сеть. Пока брокер лежит, события
   ждут в очереди клиента и уходят, когда он поднимется (тест
   `Kafka.CommandsWorkWhileBrokerIsDown`: сто сообщений меньше чем за секунду).
2. Очередь ограничена: `KafkaOptions::max_queued`, по умолчанию 100 000.
3. Очередь полна — `send` бросает. Адаптер исключение не ловит: решение
   принимает прикладной слой. `Server::publish_events` считает событие
   потерянным (`Server::lost_events`), сообщение остаётся в комнате, отправитель
   получает `OK` (тест `Kafka.FullQueueLosesEventsButKeepsMessages`). При выходе
   `chat_cli` печатает в stderr, сколько событий потеряно.
4. Номер события в комнате адаптер расходует до `send` — даже если `send`
   бросит. Поэтому потеря при переполнении видна подписчику: после 3 придёт 5,
   и `chat_tail` напечатает `gap in #general: expected event 4, got 5 — read
   /history`. Дыра в ленте — не беда, если о ней известно: история комнаты в
   чате есть, и дочитать её можно.
5. Брокер не вернулся за пять минут — сообщение выбрасывает библиотека, и
   обработчик доставки получает отчёт с ошибкой. Он работает в фоновом потоке:
   считает потери в `atomic` и пишет в stderr первую и каждую тысячную. Номер
   такого события уже у подписчика не появится — разрыв будет виден так же.
6. При остановке сервер ждёт отправки не дольше двух секунд.

Почему не отказ отправителю: событие — уведомление о сообщении, а не само
сообщение. Сообщение уже в истории комнаты, и остальные участники увидят его в
`/history`. Отказать в отправке из-за брокера — связать доступность чата с
доступностью инфраструктуры, которая для разговора не нужна.

## Звёздочка: идемпотентный потребитель

At-least-once — гарантия брокера, а не свойство приложения. `chat_tail`
фиксирует смещение вручную (`auto_commit = false`) и только после того, как
пачка обработана: упавший до фиксации потребитель получит пачку снова. Повторы
неизбежны, и для ленты чата они заметны: одно и то же сообщение дважды.

Защита — на стороне потребителя:

- **идентификатор события** — издатель, комната, номер;
- **окно уже обработанных** (`SeenEvents`): последние N идентификаторов,
  старейший вытесняется первым (`--remember=N`, по умолчанию 100 000);
- **окно переживает перезапуск** (`--state=FILE`): идентификаторы пачки
  дописываются в файл до `commit` и читаются при запуске.

Проверка: второй потребитель другой группы с тем же файлом состояния читает
топик с начала — это и есть повторная доставка — и пропускает всё:

```
$ chat_tail --group=g1 --state=seen.txt
[1:0] #general + alice joined
[1:1] #general <alice> * alice joined (#1, notice)
[1:2] #general <alice> hello (#2, text)
^C
$ chat_tail --group=g2 --state=seen.txt
[1:0] duplicate 3fa1…07:#general:1 skipped
[1:1] duplicate 3fa1…07:#general:2 skipped
[1:2] duplicate 3fa1…07:#general:3 skipped
```

Чего это не даёт — exactly-once. Печать и запись файла не атомарны вместе:
упавший между ними потребитель напечатает пачку второй раз. Закрыть щель можно,
только сделав обработку и фиксацию одной транзакцией; в выданной обёртке
транзакций нет.

## Как смотреть

```bash
lab-stand up
./build/chat_cli alice --events   # окно 1
./build/chat_cli bob --events     # окно 2: второй сервер — свой издатель, свои номера
./build/chat_tail                 # окно 3: поток событий
lab-stand events                  # или штатным потребителем: ключ, партиция, тело
```
