# Заметки

## Этап 2. Почему тело сообщения — `std::variant`, а не `std::any`

`std::any` выглядит удобнее: в него можно положить что угодно, и для нового
вида сообщения ничего не надо объявлять заранее. В этом проекте он хуже по двум
причинам.

**Стоимость доступа.** `std::variant<TextBody, SystemNotice, Reaction>` хранит
содержимое внутри себя: размер объекта — максимум из альтернатив плюс индекс,
отдельная память не нужна. Доступ — проверка индекса и смещение. `std::any`
для всего, что не помещается в его небольшой внутренний буфер (структура со
строкой в libstdc++ не помещается), выделяет память в куче — то есть каждое
сообщение в истории стоило бы ещё одну аллокацию. Доступ идёт через
`std::any_cast`, который сравнивает `typeid`, — это дороже сравнения целого
индекса, а `/history` перебирает сотни сообщений за раз.

**Что проверяет компилятор.** Набор альтернатив `variant` известен на этапе
компиляции. `std::visit` с перегруженным набором лямбд не соберётся, если
какая-то альтернатива не обработана: появится, скажем, вложение — компилятор
покажет каждое место, где его надо учесть (`type_name`, `to_string`, `size`).
С `std::any` о новом виде сообщения узнает только тот код, который о нём знает;
остальные `any_cast` молча промахнутся во время выполнения, и сообщение просто
не отобразится.

`std::any` уместен там, где набор типов действительно открыт: например,
произвольные данные, которые библиотека лишь хранит и отдаёт обратно. У чата
набор видов сообщений закрыт и определяется протоколом, поэтому `variant`
точнее выражает намерение и дешевле стоит.
