# Модель ошибок

## Правило

Внутри ядра — в хранилище, лексере, парсере, исполнителе — ошибки только
бросаются. Решение о том, что ответить, принимается в одном месте: в функции
`handle`. Там исключение любого вида превращается в ответ клиенту, и дальше
не уходит ничего.

`handle` вызывают и цикл консольного клиента, и тесты, поэтому граница
проверяема: тесты `Handler.*` подают строки, приводящие к каждому виду ошибки,
и сверяют ответ.

С этапа 4 граница — метод `Server::handle`: сервер собрал вместе хранилище,
журнал и кэш запросов. Правило от этого не изменилось — граница одна.

Правило действует до конца курса. На этапе 15 `handle` будет вызывать сетевая
сессия, на этапе 16 — обработчик HTTP-запроса, и ошибка одного клиента не должна
ронять сервер.

## Иерархия

| Класс | Когда | Поля | Код на этапе 16 |
|---|---|---|---|
| `KvError` | корень, от `std::runtime_error` | — | 500 |
| `ParseError` | строка не разобрана | причина, исходный ввод | 400 |
| `KeyNotFoundError` | ключа нет | ключ | 404 |
| `TypeMismatchError` | операция неприменима к типу | ключ, ожидаемый и фактический тип | 409 |
| `OutOfMemoryError` | запись превысила предел хранилища | ключ, сколько нужно, предел | 507 |
| `OverflowError` | `INCR` переполнил бы `int64` | ключ, значение, шаг | 409 |

Контекст лежит в полях, а не только в тексте `what()`. По полям на этапе 16
выбирается код ответа, и разбирать для этого строку сообщения недопустимо.

`OutOfMemoryError` — не `std::bad_alloc`. Хранилище запускается с пределом
(`kvs_cli --maxmemory=1024`, как `maxmemory` у Redis) и отказывает записи,
которая его превысит, до того как что-либо изменено. Это штатное решение
программы. `std::bad_alloc` — отказ операционной системы, после которого
состояние процесса под вопросом; на границе для него своя ветка с ответом
`ERR out of memory (allocation failed)`.

`OverflowError` в постановке не было — его нашёл фаззер (см. ниже).

## Сильная гарантия в MSET

`MSET` устанавливает несколько ключей: либо все, либо ни одного. Реализация —
copy-and-swap: все записи делаются в копию хранилища, затем копия меняется
местами с оригиналом операцией, которая бросить не может.

```cpp
BasicStore next = *this;          // может бросить — оригинал не тронут
for (const auto& [key, value] : pairs) {
    next.set(key, value);         // может бросить — оригинал не тронут
}
swap(*this, next);                // noexcept — точка невозврата
```

Доказательство — тесты `Guarantee.*`. Тип `ThrowOnNthCopy` бросает на N-й
операции копирования, и тест перебирает N от 1 до числа копирований, которое
делает успешный `MSET`: при каждом N хранилище после исключения совпадает
с исходным. Второй тест делает то же с пределом памяти: `MSET`, последняя пара
которого не помещается, не записывает и первых.

Почему `swap` обязан быть `noexcept`: если последняя операция может бросить,
она перестаёт быть точкой невозврата. Если `swap` поменял таблицы, но бросил
на счётчике занятой памяти, хранилище окажется с новым содержимым и старым
учётом — сильная гарантия не просто выродится в базовую, а нарушится
инвариант. Поэтому `swap` меняет только то, что меняется без исключений:
`std::map` (его `swap` — `noexcept`), два `size_t` и `optional<size_t>`.

## Два пути: исключения и ошибка-значение

На этапе 3 разбор строки написан двумя способами:

- `parse(line)` бросает `ParseError`;
- `try_parse(line)` возвращает `Result<Command, ParseError>`.

`Result` — минимальная собственная версия `std::expected` поверх
`std::variant`: проект на этом этапе собирается под C++17, а `std::expected`
появился только в C++23. Интерфейс повторяет стандартный, и на этапе 5
замена сводится к замене имени. `std::optional` для этого не подходит: пустой
`optional` говорит «не получилось», но не говорит почему — ровно тот изъян
этапа 2, ради которого этап 3 и затевался.

Сравнение по трём пунктам.

**Читаемость.** Исключения выигрывают: успешный путь в `parse` — прямой код,
каждая проверка — одна строка `fail(...)`. В `try_parse` после каждого шага,
который может не удаться, стоит проверка и ручной возврат ошибки, и логика
разбора тонет в них. Зато по сигнатуре `try_parse` видно, что разбор может
не удаться и чем, а сигнатура `parse` об этом молчит.

**Стоимость, когда ошибок нет.** Практически одинаковая. Утилита
`kvs_error_cost` (в оптимизированной сборке) показывает 77 против 66 нс
на строку: исключение, которое не бросили, по времени бесплатно — таблицы
раскрутки лежат отдельно от кода. Когда ошибка в каждой строке, бросок
дороже примерно на порядок: 2460 против 256 нс. Вывод: исключения — для
исключительного. На этапе 15 сетевой ввод может целиком состоять из мусора,
и отказ разбора там разумнее возвращать значением.

**Проброс через десять уровней.** Исключения выигрывают с большим отрывом.
Тест `TryParse.ErrorThroughTenLevels`: исключение пролетает десять уровней
само, промежуточные функции о нём не знают. Ошибку-значение каждый из десяти
уровней обязан проверить и передать дальше — десять одинаковых строк, и
пропуск любой из них молча теряет ошибку.

Итог для проекта: ядро бросает, граница ловит. `try_parse` оставлен как
образец второго пути и как основа для этапа 15. Лексер устроен наоборот:
основная функция — `try_tokenize`, а `tokenize` — это `try_tokenize(line).value()`.
`value()` у нашего `Result` бросает саму ошибку, поэтому пути стыкуются без
перевода одного в другой.

## Звёздочка: цепочка контекста

Ошибка из глубины не знает, какая команда её вызвала: `KeyNotFoundError`
несёт ключ, но не то, что это был `GET`. Исполнитель прикладывает это знание
через `std::throw_with_nested`:

```cpp
try {
    return run_command(store, command);
} catch (...) {
    std::throw_with_nested(KvError("while executing " + describe(command)));
}
```

Граница разворачивает цепочку функциями `root_cause` и `context_of`
(`src/errors.cpp`): ответ строится по исходной причине, а контекст
дописывается в скобках:

```
> GET absent
ERR no such key: absent (while executing GET absent)
```

Это единственный `catch` внутри ядра. Правило он не нарушает: запрещено
ловить и проглатывать, а здесь ловится, чтобы бросить снова, с добавленным
контекстом. Решение о том, что ответить, по-прежнему принимает только `handle`.

## Домашнее задание: фаззер

`tests/test_fuzz.cpp` прогоняет через `handle` по тысяче входов каждого вида:
случайные байты, обрезанные команды, очень длинные ключи и значения,
невалидный UTF-8, числа на краю диапазона. Проверяется, что граница не
выпускает исключений, на каждый вход есть ответ и учёт занятой памяти
совпадает с содержимым хранилища. Зерно генератора фиксировано, поэтому
упавший прогон воспроизводится. Смысл фаззер имеет в сборке с санитайзерами.

Найденный дефект: `INCR` с шагом около `INT64_MAX` переполнял знаковое целое.
Это неопределённое поведение: санитайзер остановил прогон с
`runtime error: signed integer overflow`, обычная сборка молча выдала бы
отрицательное число. Исправление — проверка перед сложением (`checked_add`)
и `OverflowError`. Дефект закрыт тестами
`Executor.IncrOverflowIsAnErrorNotUndefinedBehaviour` и
`Handler.OverflowBecomesResponse`. Остальные виды входа дефектов не выявили.
