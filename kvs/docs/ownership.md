# Владение ресурсами

Этап 4. Ни одного `new` и `delete` в рабочем коде: всё, что выделяется, кому-то
принадлежит, и освобождается деструктором владельца.

## Кто чем владеет

| Ресурс | Владелец | Вид владения | Почему так |
|---|---|---|---|
| значение ключа (`IValue`) | `Value` в хранилище | `unique_ptr` | владелец один — запись таблицы |
| файл журнала | `AppendOnlyLog` в `Server` | поле `std::ofstream` | RAII: открыт в конструкторе, закрыт в деструкторе |
| `FILE*` при чтении журнала | `read_lines` | `unique_ptr<FILE, FileCloser>` | ресурс из C, свой делетер |
| разобранный запрос | `Server::handle`, пока команда исполняется | `shared_ptr` | владеет исполнитель |
| запись кэша | `RequestCache` | `weak_ptr` | кэш наблюдает, но не продлевает жизнь |
| `Store`, `RequestCache`, журнал | `Server` | поля | всё освобождается деструктором сервера |

`shared_ptr` в проекте ровно один — на запрос, и он оправдан: на этапе 15 один
разобранный запрос могут одновременно держать несколько сессий. Везде, где
владелец один, стоит `unique_ptr` или просто поле: подсчёт ссылок атомарен и
стоит денег, а совместное владение усложняет рассуждения о времени жизни.

## Полиморфные значения

`IValue` — абстрактный класс с виртуальным деструктором; `StringValue`,
`IntValue` и `ListValue` — наследники. Без `virtual` удаление через
`unique_ptr<IValue>` — неопределённое поведение: `unique_ptr` вызывает `delete`
по статическому типу, деструктор наследника не выполнится. Тест
`Hierarchy.DeletingThroughBaseRunsDerivedDestructor` проверяет это счётчиком.

После перехода на `unique_ptr` копирование значения сломалось бы: `unique_ptr`
не копируется. А на копировании таблицы держится сильная гарантия `MSET` из
этапа 3. Поэтому у `IValue` есть виртуальный `clone`, а обёртка `Value` пишет
копирующие операции через него. Тесты этапа 3 прошли без изменений, а
`Guarantee.MsetWithPolymorphicValues` повторяет перебор точек броска на
настоящих полиморфных значениях с бросающим `clone`.

## Журнал

`AppendOnlyLog` открывает файл в конструкторе и закрывает в деструкторе;
`open` и `close` в интерфейсе нет. Копирование запрещено (два владельца одного
файла), перемещение разрешено.

`Server` с параметром `--log=PATH` пишет в журнал каждую успешную изменяющую
команду, а при запуске сначала исполняет записи существующего журнала —
хранилище восстанавливается после перезапуска.

Закрытие доказано подсчётом открытых дескрипторов процесса
(`/proc/self/fd`): тест `Log.ClosedOnException` бросает исключение посреди
области видимости журнала и проверяет, что дескриптор закрыт, а записанное до
броска — на диске. Если бы закрытие зависело от явного `close`, бросок его
пропустил бы.

Если конструктор бросил — файл не открылся, — деструктор не вызовется: объект
не построен. Но поле `out_`, уже сконструированное, разрушится. То же на
уровне сервера: `Server.FailedConstructionLeaksNothing` проверяет, что после
броска из конструктора `Server` не осталось открытых дескрипторов.

## Пользовательский делетер

`FilePtr = unique_ptr<FILE, FileCloser>`, где `FileCloser` — функтор без
состояния. Тест `File.DeleterSize`:

| Делетер | `sizeof(unique_ptr)` |
|---|---|
| функтор без состояния | 8 — как у `FILE*` |
| лямбда без захвата | 8 |
| указатель на функцию | 16 |

Функтор и лямбда без захвата — пустые классы, и `unique_ptr` размещает
делетер как пустую базу, не занимающую места. Указатель на функцию — данные,
его надо хранить.

## Кэш на weak_ptr

`RequestCache` хранит `weak_ptr` на разобранные запросы. Пока запрос кто-то
исполняет, повторная такая же строка не разбирается заново. Как только
владелец отпустил запрос, объект уничтожается, а запись истекает.

С `shared_ptr` кэш держал бы каждый запрос вечно — утечка логическая,
санитайзер её не покажет. Истёкшие записи тоже утечка, только медленнее:
ключи-строки копятся. Поэтому `get` вычищает их, когда таблица дорастает до
порога (`Cache.GrowthIsBoundedWithoutExplicitPurge`).

`make_shared` кладёт объект и контрольный блок в одну аллокацию. Деструктор
запроса вызывается, когда умирает последний `shared_ptr`, а сам блок памяти —
только когда умрёт и последний `weak_ptr`, то есть когда `purge` удалит
запись. Ещё одна причина, по которой очистка обязательна.

## Звёздочка: цикл из shared_ptr

`tools/cycle.hpp`: клиент владеет своими подписками, подписка хранит обратную
ссылку на клиента. Вид обратной ссылки — параметр шаблона.

- `kvs_cycle_demo` — обратная ссылка `weak_ptr`: после ухода клиента живых
  объектов 0.
- `kvs_cycle_leak` — тот же код, собранный с `KVS_LEAKING_CYCLE`, обратная
  ссылка `shared_ptr`: живых объектов 2, санитайзер адресов сообщает об
  утечке 152 байт в трёх блоках. В обычную сборку не входит.

```bash
cmake --build build --target kvs_cycle_leak
./build/kvs_cycle_leak
```

Все три утечки LeakSanitizer помечает как косвенные — это почерк цикла:
каждый блок указан другим утёкшим блоком, прямой утечки нет. Тесты
`Cycle.*` показывают то же счётчиком живых объектов, без санитайзера, и в
конце разрывают цикл руками, чтобы сам тест не утекал.

Признак цикла в чужом коде: два объекта, каждый хранит `shared_ptr` на
другого — родитель и ребёнок, наблюдаемый и наблюдатель. Обратная ссылка почти
всегда должна быть `weak_ptr`.

## Домашнее задание: OwningBuffer на unique_ptr<char[]>

| | Этап 1, `char*` | Этап 4, `unique_ptr<char[]>` |
|---|---|---|
| деструктор | написан | исчез |
| копирующий конструктор | написан | остался |
| копирующее присваивание | написано (copy-and-swap) | одно присваивание по значению |
| перемещающее присваивание | написано | на оба случая |
| перемещающий конструктор | написан | остался — см. ниже |
| строк кода без комментариев (`.hpp` + `.cpp`) | 63 | 54 |

Деструктор исчез: `unique_ptr<char[]>` сам вызовет `delete[]`. Два
присваивания слились в одно, принимающее параметр по значению: при `a = b` он
строится копированием, при `a = std::move(b)` — перемещением, и остаётся
обменяться с ним.

Копирующий конструктор остался, потому что `unique_ptr` не копируется:
глубокую копию за нас никто не сделает.

Перемещающий конструктор остался, хотя `unique_ptr` перемещается сам, — и это
главное наблюдение задания. Инвариант класса связывает два поля: если буфера
нет, `size_` обязан быть нулём. Сгенерированное перемещение передало бы
указатель и скопировало `size_`, и в источнике осталась бы прежняя длина при
пустом указателе. Правило нуля работает, когда каждое поле само отвечает за
свой инвариант; общий инвариант двух полей приходится охранять руками.

`make_unique<char[]>(n)` обнуляет память, `new char[n]` — нет. Здесь обнуление
лишнее: память тут же перезаписывается. В C++20 для этого есть
`make_unique_for_overwrite`; на C++17 приходится платить.
