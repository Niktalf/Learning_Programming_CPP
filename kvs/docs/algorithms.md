# Алгоритмы вместо циклов (этап 8, пункт 5)

Правило, по которому шёл проход: цикл заменяется алгоритмом, если у цикла
есть имя — «найти первый такой», «посчитать такие», «удалить такие»,
«свернуть в одно значение», «преобразовать каждый». Имя алгоритма в коде
говорит, что делается, а цикл заставляет читателя восстановить это по телу.
Если имени у цикла нет — это конечный автомат, разбор с откатом, обход с
побочными действиями на каждом шаге, — цикл остаётся, и ниже сказано почему.

## erase-remove и `std::erase_if`

Идиома erase-remove — для последовательных контейнеров:

```cpp
v.erase(std::remove_if(v.begin(), v.end(), pred), v.end());
```

`remove_if` ничего не удаляет: он сдвигает оставляемые элементы в начало и
возвращает итератор на новый конец, а хвост — элементы в неопределённом
(перемещённом) состоянии. Удаляет их `erase`. Забыть `erase` — частая ошибка:
размер вектора не меняется, а в хвосте мусор. Для `map` и `unordered_map`
`remove_if` не годится вовсе — ключи константны, переставлять элементы
нельзя, — и до C++20 удаление по условию писали циклом с `it = m.erase(it)`.

C++20 закрыл оба случая одной функцией: `std::erase_if(container, pred)`
перегружена для всех стандартных контейнеров, сама выбирает правильный
способ и возвращает число удалённых. В KVS она стоит в кэше запросов: из
ассоциативного контейнера удаляются записи, чей `weak_ptr` истёк.

## SCAN на алгоритмах

```cpp
const Iterator first(engine_.get(), engine_->first_from(cursor));
const Iterator last(engine_.get(), engine_->first_from(stop));
std::ranges::copy(std::ranges::subrange(first, last) | std::views::filter([pattern](const std::string& key) {
                      return glob_match(pattern, key);
                  }),
                  std::back_inserter(page.keys));
```

Страница — диапазон итераторов хранилища от первой позиции в корзине
`cursor` до первой позиции в корзине `stop`. Ни одного ручного цикла: шаг по
позициям движка спрятан в итераторе этапа 7, фильтр — в представлении,
сбор — в `copy`. Гарантии SCAN при рехешировании — docs/hashing.md.

## Что осталось циклами и почему

- **Лексер** (`lexer.cpp`) — конечный автомат: пробелы, кавычки,
  экранирование. Положение в строке меняется по-разному в зависимости от
  состояния, и ни один алгоритм это не выражает; `views::split` не умеет
  кавычек.
- **Сопоставление с образцом** (`glob.cpp`) — разбор с откатом к
  последней звёздочке. Это алгоритм сам по себе, и его цикл — его
  реализация.
- **Цепочка вложенных исключений** (`errors.cpp`) — следующий элемент
  получается из предыдущего (`rethrow_if_nested`), диапазона заранее нет.
  Можно было бы написать генератор, но он скрыл бы простой цикл за
  сложной обёрткой.
- **Собственные таблицы** (`chained_table.hpp`, `open_table.hpp`) — обход
  цепочки и пробег по ячейкам. Это и есть реализация поиска, на который
  опираются алгоритмы снаружи.
- **`bytes.cpp`, сдвиги по 8 бит** — тело зависит от номера шага, а не от
  элемента; `transform` здесь уже стоит снаружи, цикл внутри — арифметика.
- **`main.cpp`** — разбор аргументов командной строки и цикл чтения
  `getline`: оба — «пока есть вход, сделать действие с побочным эффектом».
- **Восстановление по журналу** (`server.cpp`) — нужен номер строки для
  сообщения об ошибке; `views::enumerate` был бы честной заменой, но
  `for` с индексом читается не хуже, а try/catch внутри тела лямбды —
  хуже.
- **`mset`** — тело может бросить, и от того, на каком ключе бросило,
  ничего не зависит: копия выбрасывается целиком. `ranges::for_each` здесь
  ничего не добавляет к `for` по диапазону.
- **`Shape` в `registry.hpp`** — `constexpr`-лямбда над массивом флагов
  при компиляции; `find_if` по `views::iota` вышел бы длиннее и не
  понятнее.
- **`Store::for_each`** — обход позициями движка с вызовом функции на
  каждую пару ключ — значение; итератор хранилища отдаёт только ключи, и
  заводить второй итератор ради одной функции незачем.
