# Этап 6: реестр команд

До этапа 6 команда проходила три места: структура в `command.hpp`, ветка в
`parse` и ветка в `std::visit` исполнителя. Добавить команду — поправить три
файла и не забыть ни одного. Реестр сводит это к одной строке:

```cpp
table.add("APPEND", Effect::Writes, append);
```

и функции-обработчику рядом:

```cpp
Response append(Store& store, std::string_view key, std::string_view suffix);
```

Арность, разбор аргументов, сообщение об ошибке и контекст для цепочки
исключений реестр выводит из сигнатуры сам. Обработчик получает уже
разобранные аргументы нужных типов и ни одной проверки формы не содержит.

Файлы: `include/kvs/function_traits.hpp`, `include/kvs/convert.hpp`,
`include/kvs/registry.hpp`, `src/commands.cpp`. Старые `command.hpp`,
`parser.*` и `executor.*` удалены — все команды идут через реестр.

## Как реестр узнаёт сигнатуру

`function_traits<F>` — шаблон с частичными специализациями для каждой формы
вызываемого объекта: указатель на функцию, тип функции, указатель на метод
(`const`, не `const`, `noexcept`) и класс с `operator()`. Последняя
специализация ограничена `requires { &F::operator(); }` и сводится к
специализации для указателя на метод — так лямбда и функтор получают
сигнатуру своего `operator()`.

Основной шаблон пустой. Для обобщённой лямбды `&F::operator()` не
вычисляется — у шаблона нет адреса без аргументов, — специализация не
подходит, и `function_traits<F>::result` не существует. Тест
`FunctionTraits.GenericLambdaHasNoSignature` это закрепляет, и реестр такой
обработчик отвергает первым же требованием концепции.

## Разбор аргумента: `if constexpr` против `enable_if`

`convert<T>(token)` — один шаблон с ветками `if constexpr`: `string_view`,
`string`, арифметический тип, иначе `static_assert(false)`. Порядок веток
существен: специальное раньше общего. В варианте C на этом этапе это видно
воочию — ветка для `Priority` стоит выше `is_arithmetic_v`.

Две детали:

- `bool` исключён концепцией `ScalarArgument` явно: `is_arithmetic_v<bool>`
  истинно, а `from_chars` его не разбирает;
- проверка `end != last` после `from_chars` обязательна: иначе «12abc»
  разбиралось бы как 12. Тест `Convert.TrailingGarbageIsRejected`.

`static_assert(false)` в отброшенной ветке законен с C++23 (P2593). До него
он срабатывал при разборе шаблона, и писали зависимое выражение вроде
`sizeof(T) == 0`.

Та же функция в историческом виде — `include/kvs/legacy_convert.hpp`: три
перегрузки на `std::enable_if`. Сравнение:

| | `if constexpr` + концепция | `enable_if` |
|---|---|---|
| Где правило выбора | в одном месте, ветки по порядку | в условии каждой перегрузки |
| Добавить случай | одна ветка | новая перегрузка и исключение её во всех прочих |
| Неподдерживаемый тип | ошибка с именем концепции в строке вызова | «no matching function» и по кандидату на перегрузку |
| Порядок предпочтения | порядок веток | нет: условия обязаны быть взаимоисключающими |

Чтобы добавить в историческую версию третий случай — `optional`, —
пришлось дописать `!is_optional<T>` в условия двух первых. Тест
`Convert.LegacyAgreesWithModern` проверяет, что обе версии ведут себя
одинаково на одних и тех же токенах.

## Форма параметров

После контекста параметры обработчика — в таком порядке:

1. обязательные: `string_view`, `string`, числа;
2. необязательные: `std::optional<T>`;
3. `Rest` — все оставшиеся токены, только последним.

Из этой формы реестр выводит арность и текст ошибки: «SET expects 2
arguments», «INCR expects 1 to 2 arguments», «MSET expects at least 1
argument». Нарушение порядка — обязательный после необязательного, `Rest` не
последним — ошибка компиляции при регистрации (`detail::Shape::valid`
вычисляется в `constexpr`-лямбде).

Правила самой команды, которые формой не выражаются, остаются в обработчике.
Пример — чётность аргументов `MSET`: «не меньше одного» выводит реестр, «пары
ключ–значение» проверяет `set_many`.

## Концепция `CommandHandler`

Пять требований, у каждого своё имя:

```cpp
template <class F, class Context>
concept CommandHandler = HasSignature<F> && ReturnsResponse<F> &&
                         TakesContextFirst<F, Context> && ArgumentsSupported<F> &&
                         ArgumentOrderValid<F>;
```

Конъюнкция проверяется слева направо и останавливается на первом
невыполненном, поэтому следующие требования могут рассчитывать на
предыдущие. Именованные требования вместо одного большого выражения — ради
диагностики: GCC 15 на `tests/compile_fail/bad_handler.cpp` (параметр `bool`)
пишет

```
required for the satisfaction of 'ArgumentsSupported<F>'
    [with F = kvs::Response (*)(kvs::BasicStore<kvs::Value>&, bool)]
```

— 23 строки вывода, и строка с невыполненным требованием указывает на `add`
в коде студента. С одним выражением на месте пяти диагностика сообщала
только «HandlerSignature<...>::value evaluated to false», и разбираться,
какое из условий не выполнено, приходилось вручную.

Тест `kvs_bad_handler_fail` в ctest проверяет и сам отказ сборки, и то, что
в выводе есть `ArgumentsSupported`.

## Разбор и исполнение по-прежнему разделены

`bind(tokens, line)` разбирает аргументы и возвращает связанную команду —
`Bound`: имя, эффект, контекст для цепочки ошибок и действие с уже
разобранными аргументами. Ошибки здесь — только `ParseError`. Вызов
`bound(store)` исполняет команду; ошибки здесь — ошибки хранилища, обёрнутые
`throw_with_nested` в «while executing GLAGOL first-argument».

Разделение нужно кэшу запросов этапа 4: он хранит связанную команду, а не
строку. Аргументы связанной команды — `string_view` внутрь строки, а `Rest` у
`MSET` смотрит ещё и в вектор токенов. Поэтому `Request` владеет всеми тремя
полями — строкой, токенами, связанной командой — и объявляет их в этом
порядке: порядок объявления — порядок инициализации. Тест
`Cache.CachedCommandOutlivesNothingItBorrows` исполняет кэшированный `MSET`
дважды под санитайзером адресов.

`Bound` знает эффект команды — `Effect::Reads` или `Effect::Writes`, — и
`Server::handle` пишет в журнал только те, что пишут. Раньше это решала
функция `modifies` с собственным `visit`; теперь эффект указан там же, где
команда зарегистрирована, и забыть его нельзя.

## Что поменялось в поведении

- Контекст ошибки одинаков для всех команд: глагол и первый аргумент. `MSET a
  1 b 1234567` за пределом памяти — «while executing MSET a»; до реестра
  было «MSET a b».
- `ParseError` от разбора числа несёт в `input` сам токен, а не всю строку:
  «not a number: 12abc».
- Текст ошибки арности для команды с необязательным аргументом — «1 to 2
  arguments» вместо «1 or 2».

## Домашнее задание: APPEND, STRLEN, GETSET

Каждая — одна строка регистрации и функция в `src/commands.cpp`.

`GETSET` устроен иначе двух других: это не `get`, а затем `set`, а одна
операция хранилища `exchange`. Сейчас разницы не видно — поток один. На
этапе 11 хранилище станет общим для потоков, и между `get` и `set` другой
поток успел бы записать своё значение; оно потерялось бы, а клиент получил бы
«старое» значение, которого в хранилище уже не было. `exchange` пройдёт под
одним захватом мьютекса. Гарантия у неё сильная: копия старого значения
снимается до записи, и если запись бросит (предел памяти), хранилище
прежнее — тест `Commands.GetsetOverMemoryLimitChangesNothing`.

## Звёздочка: `StaticRegistry`

`include/kvs/static_registry.hpp`. Имя команды — параметр шаблона:

```cpp
using Commands = StaticRegistry<Tally,
                                Command<"BUMP", bump, Effect::Writes>,
                                Command<"SHOW", show, Effect::Reads>>;
```

Строковый литерал параметром шаблона быть не может — нужен структурный тип.
`FixedString<N>` — открытый массив символов с неявным конструктором из
литерала; `N` выводится из длины литерала (C++20, P0732).

Повтор имени без учёта регистра — `static_assert` с текстом «StaticRegistry:
duplicate command name»: проверка — `constexpr`-функция над массивом имён.
Тест `kvs_duplicate_command_fail` собирает пару «BUMP» и «bump» и ждёт
именно этот текст. У обычного реестра тот же повтор — `std::logic_error` при
запуске, тест `Registry.DuplicateNameIsALogicError`.

Разбор и исполнение `StaticRegistry` не повторяет: внутри он строит обычный
`CommandRegistry` из пакета команд, и поведение двух реестров одинаково по
построению. Своё у него — только то, что известно при компиляции: проверки,
`size()` и `contains()`, которые работают в `static_assert`.

Почему рабочий реестр KVS остался динамическим: на этапе 15 сетевые команды
регистрирует сетевой слой, а на этапе 16 маршруты — HTTP-слой. Состав
реестра собирается из разных единиц трансляции и при компиляции одной из них
неизвестен.
