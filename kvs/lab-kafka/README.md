# lab_kafka — обёртка над клиентом Kafka для практикума

Студенты получают её готовой. На этапе 10 они пишут только адаптер, который
превращает доменное событие в пару «ключ — тело», и потребителя, который эти
события печатает. Всё, что связано с самим брокером, спрятано здесь.

Обёртка не содержит ничего доменного и одна на все три варианта проекта.
Каждый вариант пишет в свой топик:

| Вариант | Топик | Потребитель студента |
|---|---|---|
| A — KVS | `kvs.events` | `kvs_tail` |
| B — CHAT | `chat.events` | `chat_tail` |
| C — TASKQ | `taskq.events` | `taskq_tail` |

## Установка

Студент ставит обёртку и стенд на свою виртуальную машину сам, одной командой,
с буквой своего варианта:

```bash
unzip lab-kafka.zip
cd lab-kafka
./install.sh A        # A, B или C
```

Скрипт запускается от своего пользователя, без sudo: пароль он спросит сам там,
где он нужен. Повторный запуск безопасен. По шагам:

1. Проверяет CMake (не старше 3.28), Ninja, компилятор, Docker и группу docker.
   Если нет librdkafka-dev — ставит пакет.
2. Собирает обёртку и прогоняет самопроверку (около минуты).
3. Устанавливает в /usr/local заголовок, библиотеку, пакет CMake, заготовки
   адаптера, утилиты `lab_kafka_probe` и `lab-stand`.
4. Кладёт в /opt/lab-env файл docker-compose.yml своего варианта и запоминает
   топик. Прежний compose-файл сохраняется рядом с суффиксом .bak; контейнер
   lab-kafka от старой установки стенда (например, из /opt/kvs-env) удаляется.

После установки:

```bash
lab-stand up       # поднять Kafka и создать топик варианта
lab-stand check    # записать сообщение и прочитать обратно: СТЕНД РАБОТАЕТ
lab-stand events   # смотреть события в топике: ключ, партиция, тело
lab-stand down     # остановить
```

Библиотека modern-cpp-kafka v2024.07.03 лежит в архиве (third_party/), поэтому
версия, установленная в /opt образа, на сборку не влияет.

## Ручная сборка

То же, что делает install.sh в шагах 2–3:

```bash
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure      # самопроверка, около минуты
sudo cmake --install build --prefix /usr/local
```

После установки библиотека видна любому проекту:

```cmake
find_package(lab_kafka REQUIRED)
target_link_libraries(<цель infrastructure> PRIVATE lab::kafka)
```

### Самопроверка без стенда

`lab_kafka_selftest` поднимает внутри процесса макет кластера Kafka из
librdkafka. Макет слушает TCP-порт и говорит по настоящему протоколу, так что
обёртка проходит тот же путь, что и со стендом. Проверяется:

- сообщения с одним ключом попадают в одну партицию и читаются по порядку;
- ключ и тело доходят байт в байт — табуляция, перевод строки, нулевой байт;
- пустой топик отвергается в конструкторе, перемещённый объект — при вызове;
- деструктор дожидается отправки, а при лежащем брокере укладывается
  в `shutdown_flush` и сообщает об ошибке по каждому невыброшенному событию;
- при лежащем брокере `send` не блокируется, события досылаются после подъёма;
- переполнение очереди даёт немедленный `Error`, а не ожидание;
- ручная фиксация смещения: без `commit` повтор, после — нет;
- потребитель, убитый без закрытия, не мешает перезапуску войти в группу;
- недоступный брокер при создании потребителя — `Error` через `join_timeout`.

Цель собирается, только если в системе есть `librdkafka/rdkafka_mock.h`.

### Проверка стенда

```bash
lab-stand up
lab-stand check                     # то же, что lab_kafka_probe <топик варианта>
# брокеры: localhost:9092
# топик:   kvs.events
#   доставлено: партиция 1, смещение 0
#   прочитано обратно: партиция 1, смещение 0
# СТЕНД РАБОТАЕТ
```

Номер партиции может быть любым от 0 до 2.

## Использование

### Публикация

```cpp
#include "lab/kafka/event_bus.hpp"

lab::kafka::Producer producer({.topic = "kvs.events"});

producer.on_delivery([](const lab::kafka::DeliveryReport& r) {
    if (!r.ok) { /* решение о поведении при сбое — за вами */ }
});

producer.send("user:42", "changed\tuser:42\tstring");
```

Топик обязателен. Если его не указать в назначенном инициализаторе, компилятор
с `-Wextra` предупредит о пропущенном поле, а конструктор бросит `Error`.

`send` не выполняет сетевых операций в вызывающем потоке и не блокируется,
даже когда брокер лежит: сообщение ставится в очередь и уходит фоново. Это
важно для этапа 11: держать мьютекс шарда во время отправки нельзя, но и не
придётся.

### Чтение

```cpp
lab::kafka::Consumer consumer({.topic = "kvs.events", .group_id = "kvs-tail"});

while (running) {
    for (const auto& r : consumer.poll(std::chrono::milliseconds(500))) {
        std::cout << r.key << " -> " << r.value << '\n';
    }
}
```

Конструктор ждёт, пока брокер назначит потребителю партиции. Обычно это 1–3
секунды. Если перед этим тот же потребитель был убит по Ctrl+C, ожидание
вырастает до 6–8 секунд: брокер должен сначала убедиться, что старый участник
группы мёртв.

Пустой результат `poll` — штатная ситуация, а не ошибка: он означает, что за
отведённое время ничего не пришло.

### Журнал клиента

Служебные сообщения клиента Kafka уходят в stderr с префиксом `[kafka]`, и
только уровня «предупреждение» и выше. В stdout обёртка не пишет ничего, так
что вывод `*_tail` остаётся чистым. Если брокер лежит, в stderr раз в
несколько секунд будет строка вида `Connect to ... failed: Connection refused` —
это нормально и помогает понять, что происходит.

## Что осталось студентам

Обёртка намеренно не решает за них четыре вещи, каждая из которых входит в
постановку этапа 10:

1. **Выбор ключа сообщения.** От него зависит партиционирование, а значит и
   то, сохранится ли порядок событий. Обёртка ключ не придумывает.
2. **Поведение при недоступном брокере.** `send` не блокируется; если брокер
   не вернётся за 5 минут, обработчик доставки получит отчёт с ошибкой.
3. **Поведение при переполнении очереди.** `send` бросает `Error`. Ждать,
   копить у себя, терять или отказывать клиенту — любой выбор допустим, если
   он сделан осознанно и описан в docs/events.md.
4. **Формат тела сообщения.** Обёртка передаёт байты и не знает, что в них.

## Ограничения

- Транзакции не поддерживаются: гарантия exactly-once на этой обёртке
  недостижима. Для практикума достаточно at-least-once, а идемпотентность
  обеспечивается на стороне потребителя — это звёздочка этапа 10.
- Обработчик доставки вызывается из фонового потока библиотеки. Всё, к чему
  он обращается, должно быть потокобезопасным. На этапе 10 многопоточности
  ещё нет, на этапе 11 она появится — и это станет заметно.
- Одного продюсера на процесс достаточно: он потокобезопасен. Заводить
  по продюсеру на поток не нужно и вредно.
- Обёртка требует C++20 (назначенные инициализаторы).
